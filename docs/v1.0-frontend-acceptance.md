# V1.0 前端人工验收清单

本清单验证本地 HTTP 退款沙箱的浏览器闭环，不涉及真实资金。后端配置、签名协议、迁移边界和沙箱控制接口以 [`refund-sandbox-runbook.md`](./refund-sandbox-runbook.md) 为准。不要把沙箱 API Key、Webhook Secret、JWT 或数据库连接信息粘贴到浏览器、截图或客服消息中。

## 1. 准备环境

1. 确认根 `.env`、`apps/agent-core/.env` 和 Prisma 指向同一个开发数据库，测试数据库不能混用。
2. 在项目根目录检查并部署 migration：

   ```bash
   pnpm --filter @ecommerce-agent-system/database exec prisma migrate status
   pnpm --filter @ecommerce-agent-system/database exec prisma migrate deploy
   ```

3. 按 `docs/refund-sandbox-runbook.md` 配置本地沙箱变量。沙箱 API Key 和 Webhook Secret 必须不同，且只保存在服务端环境中。
4. 在 Cursor 的三个终端分别启动：

   ```bash
   cd apps/agent-core
   .venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
   ```

   ```bash
   cd apps/agent-core
   .venv/bin/python -m uvicorn app.refund_sandbox_app:app --host 127.0.0.1 --port 8001
   ```

   ```bash
   pnpm --filter @ecommerce-agent-system/web dev
   ```

5. 打开 `http://localhost:3000`。本次前端实现和自动化验证没有替你启动上述服务，也没有迁移或清空开发库。

## 2. 客户申请与管理员审批

1. 用 `customer.demo@example.com` 登录，查询客户自己的可退款订单。
2. 创建退款申请并完成客户二次确认。记录界面显示的退款申请编号。
3. 确认页面只显示“等待人工审批”，没有显示“已退款”或资金成功。
4. 退出并用 `admin.demo@example.com` 登录。顶部应出现“退款运维”按钮；CUSTOMER 和 SUPPORT 不应看到它。
5. 打开退款运维，在“审批申请”输入退款申请编号和备注，先点“准备批准”，再点“确认批准”。
6. 切回客户账号并重新查询订单。申请应恢复为“审批已批准”，同时资金执行区应明确显示尚未执行。

当前后端没有 ADMIN 的待审批列表/审批前详情读取接口，因此管理员需要使用客户提供的申请编号；审批结果中的金额、币种和状态仍以后端响应为准。

## 3. 成功回调闭环

1. 客户在资金执行区点“开始执行退款”，核对提示后再点“确认执行退款”。连续点击不应产生第二次提交。
2. 预期状态为 `PROCESSING`，文案为等待最终结果或签名回调，不应显示成功。
3. 在端口 8001 按 runbook 查询 `refund:{application_id}`，再 settle 为 `SUCCEEDED` 并 deliver 对应事件。
4. 回到浏览器点“刷新状态”。应显示 `退款执行成功`、原始金额/币种和沙箱参考号。
5. 刷新浏览器并重新查询订单。成功状态应从服务端恢复，不依赖浏览器本地推断。

## 4. 失败、断线与未知结果

失败链需要另一份合法已批准申请；同一用户同一订单已有非 REJECTED 申请时不能重复创建。请使用另一测试订单/用户，或在可恢复的开发库备份上重新准备数据，不要用 SQL 强改终态。

1. 对新的已批准申请执行退款，在沙箱 settle 为 `FAILED` 并 deliver。
2. 浏览器刷新状态后，只有服务端明确返回 `FAILED` 时才应显示“退款执行失败”。
3. 验收网络未知结果时，在执行请求期间临时停止 8001 沙箱或制造请求超时。页面应显示“结果暂时未知”，只提供“查询执行状态”，不能显示失败，也不能自动重新投递退款。
4. 恢复沙箱后点“查询执行状态”或对已有 `RUNNING/PROCESSING` 记录点“补查沙箱结果”。补查只查询原退款键。
5. 重新加载页面，确认 `PENDING/RUNNING/PROCESSING/SUCCEEDED/FAILED` 均由服务端记录恢复。

## 5. 丢失回调与人工队列

1. 对一份新申请执行并 settle，但不要 deliver 回调。
2. 等补偿任务到期后，在 `apps/agent-core` 运行一次有界任务：

   ```bash
   .venv/bin/python -m app.refund_reconciliation_cli --scheduled --limit 10
   ```

3. 如果沙箱查询能得到终态，客户刷新后应收敛到成功或失败，管理员队列不应长期保留该项。
4. 要验证 `NOT_FOUND` 人工路径，可在提交执行前停止沙箱，使本地保留未知执行但提供方没有记录；恢复沙箱后按配置次数运行到期补查，直到进入 `MANUAL_REQUIRED`。
5. ADMIN 刷新“退款人工队列”，打开该项，检查执行状态、补偿状态、错误码和字符串审计 ID。
6. “恢复有限补查”要求 1～500 字符备注；成功后界面应重新读取，处理项离开人工队列或状态发生变化。
7. 只有 `RUNNING + MANUAL_REQUIRED + NOT_FOUND` 才显示“原键重投”。输入备注后仍需勾选明确确认；提交内容不得包含金额或新幂等键。成功 204 后界面重新读取详情。
8. 若已有后端测试数据处于 `TERMINAL_CONFLICT`，界面只显示“确认已核查矛盾”；成功后终态必须保持原值，审计追加确认记录。矛盾数据的安全构造与签名要求见 runbook，不能通过前端伪造。
9. 审计超过 50 条时点“加载更多审计”，确认下一页没有重复覆盖前一页，超出 JavaScript 安全整数的 ID 仍完整显示。

## 6. 权限与错误边界

1. CUSTOMER 和 SUPPORT 不显示退款运维按钮；直接访问 BFF 仍应由 Agent Core 返回 403，不能只依赖隐藏按钮。
2. Access Token 过期时应自动刷新并最多重试原请求一次；Refresh Token 失效后回到登录页。
3. 401、403、404、409、429 和 503 应显示稳定中文错误。429 若带 `Retry-After`，现有认证请求层不得将其误当作 401 刷新。
4. 在运维写操作处理中重复点击，前端只发送一次请求。409 后刷新详情，不应在前端强行改变状态。
5. 关闭 Agent Core 验证 503/网络错误；页面不得显示后端 URL、数据库信息、沙箱密钥、Webhook Secret 或原始异常。

## 7. 验收记录

记录每个场景的账号角色、申请编号、执行状态变化、是否刷新恢复及实际错误码。只有本清单和后端 runbook 的关键路径完成后，才可把整个 V1.0 标记为人工验收通过。真实支付渠道、生产密钥管理、会计调整和正式审批队列不在本次范围。
