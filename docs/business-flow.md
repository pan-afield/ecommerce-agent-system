# 电商 Agent 系统完整业务流

> 对应当前 V1.0 代码，更新于 2026-09-22。本地支付服务是 HTTP 沙箱，不涉及真实资金。本文件描述已经实现的业务行为；版本验收状态以 [开发进度](./development-roadmap.md) 和 [V1.0 验收记录](./v1.0-frontend-acceptance.md) 为准。

## 1. 一眼看懂系统

一名用户登录后，可以聊天咨询、查询自己的订单和物流、检索企业知识、申请退款。退款必须依次通过客户确认和管理员审批，审批通过后才允许客户启动独立的资金执行。沙箱的最终结果通过签名回调或补查写回数据库；无法确认结果时进入有界补偿，必要时由管理员处理。

```text
浏览器（聊天 / 订单 / 知识库 / 退款）
  -> Next.js /api/* BFF（HttpOnly Cookie、上游代理、响应校验与错误映射）
  -> FastAPI /v1/*（JWT 验证、角色与归属校验、业务规则）
     -> LangGraph + 模型 / 订单工具 / RAG（问答）
     -> PostgreSQL（订单、申请、执行、审计、会话和知识）
     -> Redis（知识检索缓存、聊天与检索限流；不是资金事实来源）
     -> 本地 HTTP 退款沙箱（仅审批后的执行、结果查询与签名事件）
```

| 身份 | 主要动作 | 不允许做的事 |
| --- | --- | --- |
| CUSTOMER | 查自己的订单、申请与确认退款、执行自己的已批准申请、查执行状态 | 审批申请、读取管理员运维队列或他人的订单/申请 |
| SUPPORT | 使用聊天和有权限的知识检索 | 代客户操作其退款、审批或操作管理员队列 |
| ADMIN | 审批申请，查看和处置人工队列 | 绕过客户确认或替客户改变已记录的资金终态 |

前端是否显示按钮只是交互控制；FastAPI 仍依据已认证身份、数据库角色和资源归属做最终判断。

## 2. 登录、会话与请求入口

1. 用户登录：浏览器调用 `/api/auth/login`；BFF 与 FastAPI `/v1/auth/login` 交互，将 Access/Refresh Token 保存在 HttpOnly Cookie 中。浏览器调用 `/api/auth/me` 恢复当前用户与角色。
2. 业务请求：浏览器调用同源 `/api/*`，BFF 从服务端会话取得认证信息再请求 FastAPI；FastAPI 验证 JWT，用可信 `sub` 确定用户。客户端传入的订单号、申请号或会话号都不能代替身份。
3. Access Token 失效：前端的认证请求层对 `401` 共享一次刷新操作，成功后最多重试原请求一次；刷新失败则清理页面会话并返回登录。`429` 是限流，不触发认证刷新。
4. 退出：BFF 尝试撤销后端刷新会话，并清除本地 Cookie 和当前浏览器中的聊天/退款临时上下文；即使后端暂时不可用，也会先完成本地退出。

这里有三个不同标识：`user_id` 是验签后的身份；`thread_id` 标记一段对话；`request_id` 标记一次可安全重试的请求。它们不能互相替代。

## 3. 客服对话、订单和知识库

### 3.1 对话主线

1. 用户发消息，前端携带消息、`thread_id`、`request_id` 调用普通聊天 `/api/chat` 或 SSE `/api/chat/stream`。
2. FastAPI 验证用户并检查该用户的聊天限流。Redis 可用且额度耗尽时返回 `429 + Retry-After`；Redis 不可用时业务降级继续执行。
3. LangGraph 按 `user_id + thread_id` 读取 PostgreSQL checkpoint；同一 `request_id` 已完成则复用结果，避免重试再次调用模型/工具。
4. 意图分流：订单问题进入订单工具路径；其他问题进入知识上下文准备与模型回答路径。一个 thread 中可连续追问；缺少订单号时先追问并记住待完成的订单意图。
5. 订单工具只接收业务订单号，从认证上下文取得用户身份；查询同时限定 `order_id + user_id`。前端订单卡片还从权威订单接口取得结构化详情，不从模型文本猜金额或物流。
6. 知识路径只把实际检索到的公共资料作为模型证据，并返回所用引用；有证据时提示模型证据不足应说明无法确认。**若完全没有检索到引用，当前实现会退回普通模型回答，未强制拒答**；没有引用的回答不能视为知识库确认。订单路径不附带知识引用。当前聊天的知识上下文默认限于 `PUBLIC` 文档。
7. 普通接口返回一次完整结果；SSE 依次发送完整的 `assistant` 事件与 `done` 事件，**不是逐 token 输出**。

### 3.2 独立的订单与知识工具

- 订单查询 `/api/orders/{orderId}`：读取当前用户的订单金额、状态和按时间排列的物流事件；不存在和他人订单都按不可枚举边界返回 `404`。查询订单后，页面会读取该订单已有的非拒绝退款申请用于回显；没有申请时返回 `200 + null`。
- 显式知识检索 `/api/rag/search`：按用户角色过滤可见性：CUSTOMER 见 `PUBLIC`；SUPPORT 见 `PUBLIC/SUPPORT`；ADMIN 见 `PUBLIC/SUPPORT/ADMIN`。查询用本地 LlamaIndex + sentence-transformers Embedding（当前配置 `BAAI/bge-m3`），pgvector 语义检索与关键词检索经 RRF 合并后返回来源、页码和片段引用。中文、英文都使用同一多语言模型。
- 文档导入由 CLI 处理 `.txt/.md/.pdf`，保存片段和可见性；增量导入幂等，`--rebuild` 原子替换。成功导入后清理 Redis 检索缓存。Redis 缓存命中不是权限来源，缓存键包含可见性范围、模型等检索条件。

## 4. 一笔退款从申请到最终结果

退款分成**申请审批**和**资金执行**两条状态线。`APPROVED` 只允许开始执行，绝不表示已经退款。

| 阶段 | 操作者与动作 | 权威结果 |
| --- | --- | --- |
| 查订单与资格 | CUSTOMER 查自己的订单，提交拟退款金额/币种做资格评估 | 只有本人订单、金额大于 0、不超过订单总额、币种一致且订单为 `PAID/SHIPPED/DELIVERED` 才可进入申请 |
| 创建申请 | CUSTOMER 提交 `request_id`、金额与币种 | `AWAITING_CUSTOMER_CONFIRMATION`；同一用户+请求 ID 重试返回原申请，同用户同订单只能有一份非拒绝申请 |
| 客户确认 | CUSTOMER 对自己的申请点确认 | `PENDING_MANUAL_APPROVAL`，尚无资金动作 |
| 人工审批 | ADMIN 用申请 ID 批准或拒绝，可留备注 | `APPROVED` 或 `REJECTED`；相同决定幂等返回已有结果，相反决定 `409`，不能覆盖首次审批 |
| 开始执行 | CUSTOMER 对自己的 `APPROVED` 申请二次确认执行 | 创建唯一执行记录，金额/币种取自已批准申请，固定使用 `refund:{application_id}` 作为沙箱幂等键 |
| 等待结果 | 沙箱受理、客户查询状态 | `PENDING -> RUNNING -> PROCESSING`；页面不能把其中任一状态显示成资金成功或失败 |
| 最终结算 | 沙箱 settle 后发送签名回调，或后端按原键补查 | 只有持久化权威结果才进入 `SUCCEEDED` / `FAILED`；显示金额及成功时的沙箱参考号 |

申请状态由 `refund_applications` 保存，资金状态由 `refund_executions` 保存；两个状态不能混用。执行记录不存在但申请属于本人时，`GET .../execution` 返回 `200 + null`，表示尚未执行。

### 4.1 正常成功与明确失败

在本地沙箱中，一次执行最初通常是 `PROCESSING`。沙箱端对原键 `settle` 为 `SUCCEEDED` 或 `FAILED`，生成事件并 `deliver` 给 `/v1/refund-webhooks/sandbox`。后端先校验时间戳 HMAC 签名和事件内容，再在事务中去重、更新执行状态、记录审计并处理补偿任务，提交成功才回应。沙箱的 settle 结果和主业务库状态是两份记录：没有成功回调/补查前，页面不能因为沙箱曾受理就宣称完成。

一次成功结算不能再被相反的沙箱 settle 覆盖；重复事件不会重复改变资金状态。失败分支需要另一笔合法申请，网络异常本身**不是**失败的证据。

### 4.2 超时、断线、补查与人工处理

| 观察到的情况 | 系统如何处理 | 客户/管理员看到什么 |
| --- | --- | --- |
| 执行请求超时或断线 | 保留数据库已有执行与原幂等键；不自动再次发送 `execute` | “结果暂时未知”，客户先查执行状态，不展示 `FAILED` |
| `RUNNING/PROCESSING` 尚无最终回调 | 客户可手动 `recover` 查询原键；到期补偿任务也只调用沙箱 `get_result` | 查到终态才收敛到成功/失败，未查到则继续等待 |
| 补查失败或始终查不到 | 定时调用的有限批次补偿 CLI 以租约领取、指数退避；达到最大尝试次数转 `MANUAL_REQUIRED` | ADMIN 人工队列显示执行状态、错误码与审计；这不是自动失败 |
| 提供方确实没有原键记录 | 只有 `RUNNING + MANUAL_REQUIRED + NOT_FOUND`，ADMIN 经备注和额外确认才可“原键重投” | 先查询原键；仍不存在才使用**原金额、原幂等键**重投，不创建第二笔身份 |
| 终态与后来事件矛盾 | 保留先前 `SUCCEEDED/FAILED`，追加 `TERMINAL_CONFLICT` 审计并转人工 | ADMIN 核查后“确认已核查矛盾”，只关闭人工项和追加审计，不改资金终态 |

补偿 CLI 是一次运行即退出的批处理，**当前没有常驻自动调度器**；要自动周期执行需另行配置外部调度。租约与条件更新避免两个执行者覆盖彼此；回调和补查以数据库终态为准。审计按字符串 ID 游标翻页，避免 JavaScript 大整数精度损失。

## 5. 权限、可靠性与数据归属

| 数据/机制 | 事实来源 | 关键约束 |
| --- | --- | --- |
| 用户、订单、物流、退款申请与审批 | PostgreSQL 业务表 | 所有客户查询按认证用户隔离；退款金额使用 `Decimal`，审批原子更新 |
| 聊天上下文与重试结果 | PostgreSQL LangGraph checkpoint | `user_id + thread_id` 归属；相同 `request_id` 返回既有结果 |
| 文档片段、向量与可见性 | PostgreSQL/pgvector | 检索按角色可见性过滤；引用来自实际片段 |
| 资金执行、回调事件、补偿任务与审计 | PostgreSQL | 唯一键、原子状态转换、事件去重、终态保护、租约与追加式审计 |
| 退款提供方模拟状态 | 本地 HTTP 沙箱的持久记录 | 用独立服务密钥，按固定幂等键接受相同请求；不是生产支付渠道 |
| 检索缓存与用户限流 | Redis | 可过期、可降级；不能代替上述持久事实 |

安全错误按稳定中文消息和错误码返回：无身份/越权为 `401/403`，不属于本人或不存在的资源通常为 `404`，状态冲突为 `409`，限流为 `429 + Retry-After`，上游/数据库不可用为脱敏 `503`（或超时相关响应）。前端不应向用户暴露密钥、内部地址或原始数据库异常。

## 6. 当前边界与延伸阅读

- 当前是一个角色化的 LangGraph 工作流，不是多个独立部署的 Agent；订单 Tool 是只读的，申请与退款资金写操作走明确的业务 API，不由模型直接执行。
- 聊天在无检索证据时仍可生成不带引用的普通回答；需要严格“无证据即拒答”的政策问答时，还需单独增加规则与评估。
- 本地账号和 HTTP 退款沙箱用于学习与联调；尚无正式身份提供商、生产支付渠道或真实资金验证。
- V1.0 终态矛盾处置与超过 50 条审计已通过自动化验证；开发环境缺少现成数据，浏览器人工验收尚未完成，不能据此声称整版人工验收完成。
