# V0.4 后端学习记录

## 这一版解决的问题

V0.3 的 `DEMO_USER_ID` 只是服务端固定值，不能证明请求者是谁；`thread_id` 只表示一段对话，也不能作为身份。V0.4 先用 JWT 的 `sub` 作为可信用户 ID，再让订单查询、Checkpoint 和聊天请求使用同一个身份边界。

这一版没有加入退款、RAG、Worker 或人工审批。订单查询仍然只能由明确的聊天请求触发，模型不能自行决定修改订单。

## 请求数据流

```text
HTTP Bearer Token
  -> get_current_user_id 验证 HS256、sub、exp
  -> /v1/chat 或 /v1/chat/stream
  -> ChatService
  -> SupportState(user_id, user_message, request_id)
  -> LangGraph route_intent
      -> general: ChatOpenAI，不传工具
      -> order_start: 请求订单编号
      -> order_continue: 订单模型，传入 lookup_order
  -> AIMessage.tool_calls
  -> ToolNode
  -> ToolRuntime.state[user_id] + order_id
  -> SQLAlchemy 查询订单和物流
  -> 回到订单模型生成最终回复
```

## 身份和会话归属

JWT 的 `sub` 是当前请求的可信用户 ID。调用方不能通过订单 Tool 参数传入 `user_id`；模型可见的 schema 只有 `order_id`，Tool 从 `ToolRuntime.state` 读取用户身份。

Checkpoint 使用 JSON 复合 key `[user_id, thread_id]`。因此两个请求的时间线是：

1. 用户 A 使用 `thread-1` 保存订单意图，key 是 `[A, thread-1]`。
2. 用户 B 即使提交相同的 `thread-1`，读取的是 `[B, thread-1]`，不会看到 A 的状态。

同一个 `ChatService` 可以共享无请求状态的数据库 engine 和 Tool 对象，但 Tool 不能保存“当前用户”。每次执行的用户身份必须从本次 Graph state 注入。

## Tool Calling 和幂等

订单模型节点获得 `order_tools`，一般客服节点显式传 `None`。订单模型返回 tool call 时，Graph 进入 `ToolNode`；工具结果作为 `ToolMessage` 加回消息，再回到订单模型。

带 `request_id` 的订单请求有以下不变量：只有最终文字回复才能写入 `completed_requests`。工具调用阶段可能没有文字，不能缓存空回复。

1. 请求 A 使用 `request_id=R1`，完成模型、Tool、模型循环并保存最终回复。
2. 请求 B 使用相同 thread 和 `R1` 重试，直接走 `reuse_completed_response`，不再次调用模型或 Tool。

当前 `ChatService` 用 checkpoint lock 保护同进程内的有状态执行；跨进程协调仍属于后续可靠性版本。

## SSE

`POST /v1/chat/stream` 当前建立了 `text/event-stream` 传输契约，发送一条完整 assistant 事件和一条 done 事件：

```text
event: assistant
data: {"content":"...","model":"..."}

event: done
data: {}
```

这不是 token 级流式。Adapter 已经能把 `ChatOpenAI.astream()` 的非空 chunk 按顺序生成出来，但直接绕过 LangGraph 接入路由会失去 thread 恢复、身份边界和订单 Tool 循环，因此真正的增量 Graph 流留到后续步骤。

## Python 重点

- `TypedDict` 和 `Literal` 描述 LangGraph state 的字段和有限路由结果。
- `Protocol` 让 `ChatService` 依赖可替换的模型接口，测试可注入 Fake。
- `async/await` 保证数据库、模型和 Tool 调用不阻塞事件循环。
- async generator 使用 `yield` 逐个产生 SSE 或模型 chunk；它和普通 async function 的返回方式不同。
- 闭包 Tool 保存 application-scope engine，但用户身份保持 request-scope，从 state 注入。
- `SQLAlchemyError` 在 Tool 边界被转换为稳定错误码，避免驱动层连接信息进入模型或前端。
