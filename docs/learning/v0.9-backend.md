# V0.9 后端学习记录：Redis 按用户限流

状态：第一个功能切片的行为测试通过，尚有一处 Mypy 类型冲突待用户修正；未做真实 Redis 或多进程人工验收。V0.8 已由主对话确认人工验收通过，V0.9 仍在开发中。

## 从当前问题出发

V0.7 已经有 Redis 客户端、TTL 和 RAG cache-aside。缓存可以减少重复检索，但无法限制同一个用户连续发起聊天或检索。仅用 Python 全局字典计数时，每个服务进程拥有独立额度；使用 Redis 中的计数能让连接到同一个 Redis 数据库的应用实例共享额度。

本轮沿用现有 Redis 客户端，在 `app/core/redis.py` 增加计数函数，先接普通 chat，再接 SSE 和 RAG。不新增限流框架、Pub/Sub、队列、分布式锁或业务数据表。

教学仍然一次只给一个小步骤，用户编写生产代码。Codex 在每步后阅读实际变更，等计数、入口和错误响应组成可观察的功能切片，再集中维护并执行测试、Ruff 和变更文件 Mypy。

## 已写出的请求链

```text
普通 chat / SSE：
Pydantic + JWT 身份依赖 → 取得 Redis 客户端 → 按用户计数
  ├─ 超额 → JSON 429 + Retry-After
  └─ 允许 / 未配置 Redis / RedisError → ChatService → JSON 或 SSE

RAG：
Pydantic + JWT → 数据库角色 → 可见范围和 embedding 配置检查 → 按用户计数
  ├─ 超额 → JSON 429 + Retry-After
  └─ 允许 → 缓存命中直接返回，或检索、融合并返回 citations
```

RAG 限流发生在缓存读取之前；数据库角色依赖先于计数，所以这一步并没有限制所有认证数据库查询。SSE 在流开始发送前决定是否返回 429，事件生成器中不做计数。

| 入口 | 用户计数 key | 超额错误码 |
| --- | --- | --- |
| `/v1/chat` 和 `/v1/chat/stream` | `rate:v1:chat:user:{current_user_id}` | `chat_rate_limited` |
| `/v1/rag/search` | `rate:v1:rag:user:{current_user_id}` | `rag_rate_limited` |

key 来自验证过的 JWT 用户 ID，不包含完整消息、查询词或 token。RAG 不按角色计数：两名 CUSTOMER 用户分别拥有额度。角色仍只决定 `PUBLIC/SUPPORT/ADMIN` 文档可见范围。

## 计数与时间窗口

`consume_rate_limit()` 接收 Redis 客户端、key、次数上限和窗口秒数，返回是否放行。配置是 `RATE_LIMIT_REQUESTS=30`、`RATE_LIMIT_WINDOW_SECONDS=60`，都必须大于零。RAG URL 中的 `limit=3` 是证据条数，不能用于请求次数判断。

- `INCR`：把整数计数加一；不存在的 key 从 1 开始。被拒绝的调用也已经计数。
- `EXPIRE ... NX`：只有没有 TTL 时设置过期时间，后来的调用不延长窗口。需要 Redis 7+。
- `pipeline(transaction=True)`：命令先排队，`await execute()` 才提交；结果列表按命令顺序排列。
- `results[0] <= limit`：第 N 次允许，第 N+1 次拒绝。

窗口从第一个请求开始。例如第 0 秒开启 10 秒窗口，第 4 秒和第 9.5 秒的请求都不会改变第 10 秒过期的时间。窗口失效后，下次请求重新从 1 计数。这不是滑动窗口，窗口交界处可能出现短时间内接近两倍上限的突发请求。

## 两请求并发时间线与状态范围

假设上限 30，已有 29 次计数：

| 时间 | 请求 A：普通 chat | 请求 B：SSE |
| --- | --- | --- |
| 同时到达 | 验证同一用户身份 | 验证同一用户身份 |
| Redis 顺序执行事务 | `INCR` 得到 30，放行 | `INCR` 得到 31，拒绝 |

若改成“先 GET，再 SET”，两个请求可能都读到 29、写入 30，导致额度被重复分配。`INCR` 自身是原子的；事务进一步将递增与 TTL 设置放在同一批执行中，避免应用在两次独立调用之间退出而留下没有 TTL 的计数。

不变量：Redis 正常、窗口计数未被清除时，同一用户同一 bucket 每个窗口最多放行 N 次。Redis 事务保证命令执行不被其他请求插入，但不提供 PostgreSQL 的失败回滚语义。

配置和 Redis 客户端由应用 lifespan 管理，每个应用进程有自己的客户端与连接池；持有计数的是共享 Redis。pipeline 和 `allowed` 是每次请求的局部状态。不同请求不用共享 Python pipeline，也无需另加应用内锁。

## 降级、幂等与边界

未配置 Redis 时路由继续执行；计数遇到 `RedisError` 返回 `True`。RAG 的缓存读写也会对 Redis 故障降级。这个选择优先保持业务可用，故障、Redis 重启或计数被清除期间不能保证限流上限。

`Retry-After` 使用完整窗口秒数，是保守等待时间，不是实际剩余 TTL。`chat_rate_limited` 沿用既有错误码；上游模型自身的限流也使用这个码，当前没有细分两者。

重复 `request_id` 仍算一次 HTTP 尝试。额度允许时，ChatService 可以从 Checkpoint 重放已有回答；额度不足时先返回 429，不访问模型或修改 Checkpoint。计数不等于退款/订单的业务幂等记录。PostgreSQL 继续保存订单、退款、Checkpoint 和任务等持久事实。

本轮只做已认证用户限流，没有 IP 限流，也没有改变代理头信任规则。生产 Redis 的连接超时、故障重试策略和多进程部署尚需单独验收。

## 集中验证（2026-09-15）

测试包含低层计数和真实 FastAPI 路由，Redis、数据库角色、模型全部使用 Fake/Mock，不下载 embedding 模型，不调用付费 API，不启动长期服务。

已覆盖：

- 正常请求、达到阈值、第 N+1 次返回 JSON 429，配置值校验；
- 后续请求和拒绝请求不延长 TTL，过期后恢复额度；
- 普通 chat 与 SSE 共用额度，RAG 独立额度，同角色不同用户隔离；
- 两个应用实例共享 Fake Redis，同一用户并发请求不超过上限；
- JWT/输入校验失败不消耗额度，RAG 未授权角色不进入限流或缓存；
- 缓存命中仍计数，被限流时不读取缓存或调用检索/聊天服务；
- 实际抛出 RedisError 后三个入口继续工作，RAG 缓存读写也降级；
- request_id 重放、Checkpoint 和原有 Graph 行为回归；
- 三个入口的 OpenAPI 都声明 429 响应。

结果：197 passed，Ruff 通过；Mypy 检查 8 个文件，在 `rag.py` 中发现同一原因引起的两条错误，尚未通过。

问题是限流分支先把 `response` 赋值为 `JSONResponse`，后面的成功分支又赋值为 `RagSearchResponse`。Python 的 `if` 不创建独立的局部变量作用域，Mypy 因此认为两次赋值类型冲突。应把限流分支的变量改名为 `limited_response`，保留成功响应变量，由用户完成这处生产代码修正后再复查。

Fake 的锁模拟了 Redis 事务的顺序执行，不能证明真实 Redis 版本兼容性、网络行为或跨进程部署正确；这些仍是后续人工验收项。本轮不标记 V0.9 完成。
