## V1.0 收尾：从退款结果到可恢复闭环

原来的执行记录能防止终态覆盖，但仍有三个实际缺口：只有当前状态看不到变化依据；
一次人工对账不能持续处理超时；内存提供方在重启后会忘记幂等键。
本轮分别用 PostgreSQL 审计、持久补偿任务和 HTTP 沙箱解决，不引入真实支付 SDK 或新的 Worker。

### 当前请求链

```text
客户 JWT + 已批准申请
  → 读取申请归属与已批准金额
  → 创建/复用退款执行，原子领取 PENDING → RUNNING
      ↳ 同一事务写状态审计并创建补偿任务
  → HTTP 沙箱 POST /refunds（释放数据库事务后）
      ↳ 原键 + 请求摘要持久去重，返回 PROCESSING
  → 条件更新本地状态 + 审计

沙箱模拟 settle → 保存终态 + 稳定 event_id
  → deliver 签名回调 → 事件去重 + 状态更新 + 审计 + 关闭任务（同一事务）
  或
到期补偿批次 → 原子领取租约 → GET 原键 → 校验 token → 同一事务收敛结果
  → 有限重试仍未知：MANUAL_REQUIRED → ADMIN 留痕处置
```

外部 HTTP 与本地数据库不构成同一事务。可靠性来自“持久原键 + 回查 + 原子本地提交”，
不是一次 `engine.begin()` 就能回滚远端支付。数据库 session/connection 只在一次短事务内使用；
进程共享的是连接池和 HTTP 客户端，不共享当前退款、当前用户或未提交结果。

### 两个请求的时间线与不变量

**重复执行。** A 锁住申请 X 并创建执行；B 对 X 等待。A 提交后 B 复用同一执行记录。
只有条件更新 `PENDING → RUNNING` 的赢家调用支付。这里额外锁申请行，是因为执行表同时有申请 ID、
幂等键两个唯一索引；仅指定一个 `ON CONFLICT` 目标，另一个索引仍可能在并发插入时抛错。
不变量：同申请一条执行，同键一份支付内容；不同申请不需要互相排队。

**任务超时与晚返回。** A 领取 token A，在网络中暂停；租约到期后 B 领取 token B。
B 完成后 A 才返回，A 的 token 条件不再成立，不能覆盖 B。若 webhook 先写入终态，
它会清理租约并关闭任务，晚到补查同样失效。领取使用数据库时间和 `SKIP LOCKED`，
不靠应用进程时钟或 Python 锁协调不同进程。

**审计外键与死锁。** A 正在锁执行记录、随后更新任务；B 正在领取任务、随后插入审计。
审计外键需要检查执行记录存在。状态更新不改主键，因此执行行用 `FOR NO KEY UPDATE`，
允许 B 的外键检查通过，避免 A 等 B 的任务锁、B 又等 A 的主键锁。测试用重叠连接验证了这一点。

**人工原键重投。** A 领取已耗尽且 NOT_FOUND 的人工任务；B 同时点击只能得到不符合状态。
A 先查沙箱，确实无记录时才用数据库原金额和原键重投；若旧执行此时才到，提供方唯一键合并它们。
自动补偿永远不做这一步。该保证基于本地沙箱永久保存幂等记录，真实渠道需独立确认键的有效期和查询语义。

**状态和审计回滚。** A 在事务内更新成功，trigger 已插入审计并完成任务，但提交前出现异常。
B 仍只能读到此前状态；A 回滚后，状态、审计、任务全部恢复。审计返回 ID 不代表提交已完成。
`set_config(..., true)` 在事务结束后失效，连接复用给 B 不会继承 A 的操作人。

### 审计与补偿状态

审计保留创建/基线、状态变更、查询开始/延后、转人工、人工恢复、授权重投、忽略结果及终态矛盾。
矛盾事件记录 `source_event_id` 和收到的 `provider_reference`，保留原终态，供管理员核查。
异常只记录稳定错误码或异常类型，不保存网络异常正文、密钥或 SQL 参数。
人工备注是核查依据，不应填写密钥或支付敏感信息。

任务状态为 `READY / LEASED / COMPLETED / MANUAL_REQUIRED`，不替代退款资金状态。
第五次领取后崩溃也有到期转人工路径。耗尽后迟到的可信终态可自动关闭未知任务；
已发现终态矛盾则需显式管理员确认，不能让后来的普通回调掩盖矛盾。

`GET /v1/refund-operations/{id}` 在一份 REPEATABLE READ 快照内返回执行、任务和一页审计。
审计 ID 是数据库序列号，用字符串传给前端；分页用于浏览已有历史，不是事件订阅游标。
有并发事务提交时刷新应从 `after_id=0` 重新读取，不能把序列分配顺序当作提交顺序。

## 早期内存实验（现已移除）

```text
execute_approved_refund(engine, user_id, refund_application_id, adapter)
  → 按申请 ID 读取 RefundApplicationRecord
  → 检查用户归属和 APPROVED 状态，不满足则返回 None
  → build_refund_sandbox_request 从记录取得金额、币种、用户和订单
  → 服务端构造稳定键 refund:{application.id}
  → await adapter.execute(request)
```

这一阶段还没有为这条链添加 HTTP 路由或退款 Worker，也没有将沙箱结果写回数据库。`APPROVED` 表示审批通过，不表示资金已退回；后面的持久执行编排已补上成功与处理中落库，但尚未接入路由。

`RefundSandboxRequest` / `RefundSandboxResult` 使用 dataclass 表达内部数据。类型标注供 Pylance、Mypy 检查；普通 dataclass 不会像 Pydantic 一样在构造时自动校验并转换字段类型。`frozen=True` 禁止通常的字段重新赋值，但不是授权机制。

适配器的 `Protocol` 描述异步 `execute()` 契约，测试替身只要满足方法签名即可注入，无需显式继承它。当前实现不连接支付服务，只返回带 `sandbox-` 前缀的模拟引用号。

曾出现的 Pylance 报错：初版请求把三个 ID 写成 `UUID`，现有退款记录、Prisma schema 和数据库实际使用字符串 / `VARCHAR`。现已统一为 `str`。`order-demo-001` 等数据不能用 `UUID(...)` 强行转换，类型声明应反映实际边界。

## 内存幂等的范围

每次调用的 request/result 是局部变量，`_results` 则是一个沙箱实例共享的字典。当前 `execute()` 内没有 `await` 挂起点，同一事件循环中查找和保存不会被另一个协程插入；这不保证跨线程、跨进程或重启后的幂等。

```text
请求 A：进程 1 的字典没有键 K → 创建模拟结果
请求 B：进程 2 的字典也没有键 K → 再创建模拟结果
```

同键复用结果只是一条学习行为，还没有验证同键请求内容是否一致。它不能作为真实支付幂等保证。后续必须区分“本地执行记录唯一”“任务执行权”和“支付提供方的幂等副作用”；数据库记录唯一也不能解决外部退款已成功、响应却超时的未知结果。

## Prisma 所有权与执行记录

退款执行属于传统业务表，由 `packages/database/prisma/schema.prisma` 与同目录 migration 管理。`apps/agent-core/migrations` 中的 agent 基础设施仍保持独立所有权。

新增 migration 为 `20260916090000_create_refund_executions/migration.sql`，模型为 `RefundExecution`：

- `refund_application_id` 和 `idempotency_key` 分别非空且唯一，保护执行记录身份；
- ID 沿用字符串，金额沿用已批准申请的 `DECIMAL(12, 2)`；
- `provider_reference` 可空，允许尚未取得支付结果；
- 时间字段使用 `TIMESTAMPTZ(3)`，创建时由数据库填默认值；
- `updated_at` 的默认值只在插入时生效，后续 SQLAlchemy 更新需显式设置时间。

`@map` 映射字段到数据库列，`@@map` 映射模型到数据库表。migration 表达建表步骤，schema 表达目标结构，需要保持一致。

当前模型和 SQL 尚未声明申请外键、金额 CHECK 或执行状态 CHECK。编排已接入执行记录，但不要因此认为数据库本身验证了全部执行资格；批准状态和归属目前由写入 SQL 与服务调用链约束。

## 原子创建待执行记录

用户已实现 `try_create_refund_execution()`。调用方只提供执行记录 ID、可信用户 ID 和申请 ID；`INSERT ... SELECT` 从申请表中选出属于该用户且为 `APPROVED` 的记录，将金额、币种和服务端稳定幂等键写入执行表，状态为 `PENDING`。

```text
请求 A：连接 A 插入申请 X 的执行记录 → 提交成功，返回 True
请求 B：连接 B 同时插入申请 X → 若 A 提交成功则遇到唯一冲突，返回 False
```

若 A 回滚，B 仍有机会插入。不变量是同一个申请最多对应一条已提交执行记录。Python 中各请求有自己的连接与事务，唯一约束在共享 PostgreSQL 中跨连接生效。

`ON CONFLICT (refund_application_id) DO NOTHING` 只处理申请唯一键冲突，不掩盖其他错误。执行 ID 主键冲突或数据库不可用仍抛异常；不能把它们解释为安全重试。`False` 只表示没有插入，既可能是不符合申请条件，也可能是已有执行记录。

`RETURNING id` 用于判断本次是否插入；`engine.begin()` 退出上下文后提交，异常时回滚。函数内的 `return` 仍须等待上下文正常退出，提交失败不会向调用方返回成功。

此函数只准备记录，不修改申请的审批状态，也不发送支付请求。`PENDING` 是执行记录状态，与申请的 `APPROVED` 分开。尚未修改 `execute_approved_refund()`，不能把当前内存调用链视为已经接上持久化保护。

## 原子领取与数据库实测


## `FAILED` 状态的 connection-level 抽取（2026-09-18）

`FAILED` 状态也完成了同样的边界拆分：公开的 `try_fail_refund_execution()` 继续通过 `engine.begin()` 管理一次独立事务；新增的 `_try_fail_refund_execution_on_connection()` 只接收已有 `AsyncConnection`，执行原来的条件更新，不自行提交或关闭连接。

## Webhook 事件与状态原子落库（2026-09-18）

用户继续授权 Codex 完成这一功能，并保留中文函数说明。`apply_refund_webhook_result()` 现在接收完整的 `RefundWebhookEvent`，路由不再只传 `event.result`，以免丢失用于去重的 `event_id`。没有新增生产模块、锁服务、支付调用或 migration。

当前请求链：

```text
POST /v1/refund-webhooks/sandbox
  → 原始 body 签名校验 → 解析 RefundWebhookEvent
  → apply_refund_webhook_result(engine, event=...)
    → engine.begin()，取得本请求的连接
      → 按退款幂等键读取执行记录
      → 未知/PENDING：返回 None，不记录事件
      → 插入事件（event_id 唯一约束）
        → 首次事件：同一连接上校验并条件更新状态
        → 重复事件：核对幂等键、状态和提供方引用，跳过状态更新
      → 同一连接重新读取当前状态
    → 退出上下文，提交成功后才返回记录
  → 204
```

查询也拆出了接收 `AsyncConnection` 的版本，这是本步出现的具体需要：如果更新后仍用 `engine.connect()` 另开连接，查询可能读不到当前事务尚未提交的状态。原来的独立查询入口保留，新编排只使用共享连接版本。`return` 写在 `async with` 内也不会跳过退出逻辑；提交异常仍会传播，HTTP 入口不能据此返回成功。

最简单的“先调用独立事件写入函数，再调用独立状态更新函数”存在断点：事件已提交而更新失败时，重试会被事件去重错误地拦截。现在唯一约束与事务分别负责两件事：前者协调同一事件的并发插入，后者保证事件摘要与状态处理不会部分提交。

```text
请求 A（连接 A）：插入 evt-001，未提交
请求 B（连接 B）：插入 evt-001，在唯一约束处等待
分支一：A 更新状态并提交 → B 的插入返回 False → 核对事件后读取最新结果
分支二：A 更新途中报错并回滚 → B 插入成功 → 应用状态并提交
```

连接属于各次请求，engine 是应用级连接池，事件与执行状态属于共享 PostgreSQL 数据。没有引入 Python 全局锁；不同 `event_id` 仍可以描述同一退款的不同阶段，终态保护继续由条件 `UPDATE` 完成。旧事件可以作为通知摘要保存，但不能将 `SUCCEEDED`/`FAILED` 改回处理中或另一个终态；事件的 `status` 表示收到的通知，不保证等于当前执行状态。

两个补充边界：

- `PENDING` 尚未领取执行权，此时不能记录事件后返回成功，否则稍后进入 `RUNNING` 时同一事件会被跳过。未知执行或 `PENDING` 返回可重试的 503，不保存事件；准备就绪后可以重投同一 `event_id`。
- 相同 `event_id` 必须保持相同退款键、状态和引用。内容改变会抛出固定的 `ValueError`，路由映射为脱敏的 400。不能把“事件 ID 相同”直接等同于“请求内容相同”。

HTTP 请求结构保持不变。正常处理、相同事件重投以及被终态保护忽略的旧通知仍为 204；签名错误为 401；正文无效或事件内容冲突为 400；配置未就绪、未知/PENDING 执行以及数据库错误为 503。错误正文不包含事件信息、SQL 或密钥。

## 有数量上限的顺序对账批次（2026-09-18）

## 区分结果通知与实际更新（2026-09-19）

本步骤由用户明确授权 Codex 完成。当前底层三个条件更新函数已经返回 `bool`，但 `_apply_refund_sandbox_result_on_connection()` 原先丢弃了返回值。为给后续审计提供依据，本轮只将该分派函数的返回类型改为 `bool`，三个状态分支都通过 `return await ...` 传回实际更新结果，并补充中文函数说明。归属校验、成功引用号校验和原有 SQL 条件保持不变。

`await` 等待底层更新，`return` 把得到的布尔值交给调用方。`True` 表示本事务内更新了一行；`False` 表示没有符合更新条件的行，可能是重复通知、旧通知或目标不存在，不能只凭 `False` 推断具体原因。返回值不等于提交结果，函数仍不创建或结束事务。

```text
请求 A：条件 UPDATE 更新退款 K → 返回 True，尚未提交
请求 B：尝试更新 K → 等待 A 释放数据库行锁
若 A 提交终态：B 重新检查条件 → 不再符合条件，返回 False
若 A 回滚：B 仍可能更新成功，返回 True
```

因此后续审计需要根据条件更新结果判断是否发生了变更，并与状态更新处于同一事务中。不能仅根据更新前的查询快照或收到的通知写一条“已成功变更”记录。本轮未增加锁机制、审计表或审计写入；外层 `_apply_refund_sandbox_result()` 仍返回 `None`，现有调用方继续忽略内层布尔值。
