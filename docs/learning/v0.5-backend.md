# V0.5 后端学习记录：退款风控、客户确认与人工审批

## 本版目标

V0.5 在不调用支付 SDK、不让模型决定退款的前提下，完成一条可测试的退款申请流程：

1. 用户提交退款金额，服务端先做归属、金额、币种和订单状态风控判断。
2. 通过风控的申请使用 `(user_id, request_id)` 做幂等创建。
3. 客户确认后，申请进入 `PENDING_MANUAL_APPROVAL`。
4. 已验签 JWT 的审批人提交 `APPROVED` 或 `REJECTED`。
5. PostgreSQL 原子更新保证一次申请只能产生一个首次人工决定。

本版没有加入支付副作用、退款执行、LangGraph Tool Calling、RAG、Worker 或复杂 RBAC。

## 请求数据流

```text
POST /v1/orders/{order_id}/refund-applications
  -> JWT 当前用户
  -> 按 order_id + user_id 读取订单
  -> assess_refund()
  -> ON CONFLICT (user_id, request_id) DO NOTHING
  -> AWAITING_CUSTOMER_CONFIRMATION

POST /v1/refund-applications/{application_id}/confirm
  -> JWT 当前用户
  -> WHERE id + user_id + 可确认状态
  -> PENDING_MANUAL_APPROVAL

POST /v1/refund-applications/{application_id}/review
  -> JWT 验签
  -> REFUND_APPROVER_USER_ID 授权检查
  -> UPDATE ... WHERE status = PENDING_MANUAL_APPROVAL
  -> APPROVED / REJECTED
  -> 读取并返回审计字段
```

## 本版 Python / FastAPI 知识

### `Literal` 和 Pydantic 输入模型

`RefundReviewPayload.decision` 使用 `Literal["APPROVED", "REJECTED"]`，因此请求体在进入路由前就限制为两个允许值。`review_note` 使用 `Field(max_length=500)` 限制长度，并用 `field_validator(..., mode="before")` 清理首尾空白；纯空白会变成 `None`。

### Dependency 的两层边界

`get_current_user_id` 只回答“JWT 里的用户是谁”，返回 `401` 表示没有可信身份。`get_current_refund_approver_id` 再比较只读配置 `REFUND_APPROVER_USER_ID`，回答“这个已认证用户是否可以审批”，普通用户返回 `403`，未配置返回 `503`。

这是 V0.5 的临时单审批人边界，后续可替换为 JWT claims + RBAC；路由本身不再重复验签或比较配置。

### `datetime` 和 JSON

service 内部保留 `datetime | None`。响应模型也声明同样的 Python 类型，让 FastAPI/Pydantic 负责 JSON 序列化。UTC 时间在响应中可能显示为 `Z`，例如 `2026-08-23T10:00:00Z`。

### `Decimal` 的后端边界

金额从请求模型到 service 和 SQL 参数都保持 `Decimal`。Prisma 的 `Decimal(12, 2)` 与 Python 的 `Decimal` 对应；HTTP 响应由 Pydantic 序列化为稳定的金额字符串，例如 `"88.00"`。

## 并发与幂等不变量

### 创建申请

两个请求同时使用同一用户和 `request_id`：

```text
A: INSERT ... ON CONFLICT ... DO NOTHING -> 创建成功
B: INSERT ... ON CONFLICT ... DO NOTHING -> 不创建，读取 A 的记录
```

不变量：同一用户的同一幂等键不会产生两份申请；如果重试时订单、金额或币种不同，API 返回 `409`。

### 客户确认

两个确认请求都使用 `WHERE status IN (...)` 的原子更新。第一个请求把状态推进到 `PENDING_MANUAL_APPROVAL`，重复确认仍返回相同状态；申请归属同时由 `user_id` 条件保护。

### 人工审批

```text
A: UPDATE ... WHERE status = PENDING_MANUAL_APPROVAL -> APPROVED
B: UPDATE ... WHERE status = PENDING_MANUAL_APPROVAL -> 0 行
B: 读取当前状态 APPROVED
```

相同决定重试返回数据库中已保存的结果；相反决定返回 `409`。第一次审批人、时间和备注不会被后续请求覆盖。

## Prisma / SQLAlchemy 边界

Prisma 只拥有传统业务表和退款申请表的 migration。SQLAlchemy async 只读取和更新这些已存在的表，不创建表。退款审计字段由 Prisma migration `20260822085535_add_refund_review_outcomes` 增加。

人工审批更新使用 `engine.begin()` 和一条带状态条件的 `UPDATE ... RETURNING`。状态条件不是普通的“先查询再更新”，因此 PostgreSQL 可以在并发请求之间保证只有一个请求成功转换状态。

## 常见错误

- 把 `thread_id`、path 参数或请求体中的用户 ID 当成可信身份；身份只能来自已验签 JWT。
- 把审批 dependency 误写到 `application_id` 参数上，导致路径 ID 被当前用户 ID 覆盖。
- 先 `SELECT` 再 `UPDATE`，在两个并发请求之间留下重复审批窗口；应把状态条件放进同一条原子 `UPDATE`。
- 将 `False` 一律映射成 `409`，从而无法区分不存在申请和已处理申请；应先读取当前状态。
- 审批重试重新写入备注；相同决定重试应直接返回第一次持久化的审计记录。
- 在响应模型中把 `datetime` 声明为 `str` 并手动序列化，造成内部类型和模型不一致。

## 手动练习与未覆盖边界

在 Cursor 中配置真实的 `JWT_SECRET_KEY` 和 `REFUND_APPROVER_USER_ID` 后，可以用两个不同 JWT 手动调用审批接口，观察 `401`、`403`、`200` 和 `409`。不要在自动测试中填入真实支付或 OpenAI 密钥。

当前仍未实现：正式登录/注册、RBAC 审批角色、多审批人队列、支付退款执行、审批列表分页、审计事件表和跨进程任务恢复。这些属于后续版本或企业可靠性增强范围。
