# V0.8 后端学习记录：正式身份与知识权限

## 本版解决的问题

V0.4 使用的 demo identity 只能帮助我们学习订单归属和 thread 隔离。它不能回答三个正式身份问题：

1. 用户如何登录并获得短期访问令牌？
2. refresh token 如何轮换和撤销？
3. 用户角色变化后，下一次请求是否立即使用新权限？

V0.8 将身份、角色和公共知识文档权限接入现有 FastAPI 请求链。本版不接真实支付，也不引入多租户权限。

## 学习节奏

生产业务代码由用户按小步骤完成。每次只引入一个主要概念，先观察当前代码暴露出的具体问题，再决定是否增加新的边界。

测试、Ruff 和变更文件的 Mypy 按一个边界清晰、可观察的功能切片集中执行，例如登录、refresh rotation 和 logout 组成一个认证切片后再统一验证。安全、并发、事务、幂等和数据完整性边界仍在完成后立即验证。Codex 维护测试、Fake、Mock、fixtures 和学习记录。

## 1. 登录请求链

```text
POST /v1/auth/login
  -> Pydantic 清理 email 和校验 password 长度
  -> SQLAlchemy async 查询 users
  -> Argon2 校验 password_hash
  -> 签发 access token
  -> 生成 refresh token，只把 hash 写入 refresh_tokens
```

这里的关键 Python 后端知识是：

- `Annotated` 和 `StringConstraints` 把输入规范放在 Pydantic model，而不是散落在路由条件中。
- `SecretStr` 让配置对象不会在普通输出中显示密钥。
- `async def` 路由必须等待异步数据库操作；密码校验仍由 Argon2 库执行，错误映射为稳定的 401/503。
- 数据库只保存 refresh token 的哈希值，响应才返回一次明文 token。

## 2. JWT 只携带身份，不携带当前角色

access token 包含 `sub`、`exp`、`iss` 和 `token_type=access`。每个受保护请求由 `get_current_user_id()` 验证签名、issuer、类型和过期时间。

角色不放进 JWT，而是每次需要权限时查询 users 表。这让数据库角色成为当前事实来源。

两次请求的时间线：

```text
请求 A：JWT 的 sub=user-1，数据库角色=ADMIN -> 允许管理员操作
管理员撤销角色：数据库角色改为 SUPPORT
请求 B：继续使用同一个旧 JWT，重新查库 -> 403
```

不变量是“旧 token 不能绕过已经撤销的数据库角色”。代价是每次需要角色的请求多一次数据库读取；在当前学习版本中，这比把角色复制进 JWT 后等待 token 过期更容易解释和验证。

## 3. Refresh rotation 和 logout

refresh 请求在同一个 `engine.begin()` 事务中完成：

1. `SELECT ... FOR UPDATE` 锁定旧 token；
2. 确认 token 未撤销且未过期；
3. 将旧 token 写入 `revoked_at`；
4. 插入新的 token hash。

两个并发 refresh 请求不能同时成功使用同一个 refresh token。事务提交后，第二个请求读到已撤销状态并返回 401。logout 只撤销数据库中的 token，之后 refresh 会失败。

## 4. FastAPI dependency 的边界

`get_current_user_id()` 负责“这个请求是谁”，`get_current_user_role()` 负责“这个用户当前是什么角色”。订单、退款、聊天和 RAG 路由复用身份依赖，不接受客户端传入的 user id 作为归属依据。

这两个依赖属于请求范围；数据库 engine 和 Redis client 属于应用 lifespan 创建的共享资源。请求之间不共享可变的用户对象，角色和 token 状态由数据库与 JWT 验证重新得到。

## 5. 知识库 visibility

`knowledge_chunks` 增加 `visibility`，允许值为 `PUBLIC`、`SUPPORT`、`ADMIN`，默认值是 `PUBLIC`。知识块仍是公共知识结构，没有 `user_id` 或 `tenant_id`。

RAG 请求链如下：

```text
JWT -> 查询 users.role -> 计算可见范围
    -> 语义检索和关键词检索都带 visibility IN (...)
    -> 稳定融合 -> 返回 citations
```

角色和范围固定为：

| 角色 | 可见范围 |
| --- | --- |
| CUSTOMER | `PUBLIC` |
| SUPPORT | `PUBLIC`, `SUPPORT` |
| ADMIN | `PUBLIC`, `SUPPORT`, `ADMIN` |

两个请求的缓存风险：

```text
请求 A：ADMIN 查询并缓存三类文档
请求 B：CUSTOMER 查询相同关键词
```

如果 key 只有 query，B 可能读到 A 的结果。当前 RAG cache key 包含排序后的 visibility scope，因此三类用户使用不同 key。缓存是加速层，权限过滤仍在数据库检索链路中完成；Redis 故障时回源数据库，不改变授权结果。

## 6. 文档导入验收

`apps/agent-core/tests/fixtures/rag-visibility/` 提供三份无敏感信息的本地文档。导入时由 CLI 明确指定范围：

```bash
cd apps/agent-core
.venv/bin/python -m app.rag.ingestion_cli \
  --visibility PUBLIC tests/fixtures/rag-visibility/public-policy.md
.venv/bin/python -m app.rag.ingestion_cli \
  --visibility SUPPORT tests/fixtures/rag-visibility/support-policy.md
.venv/bin/python -m app.rag.ingestion_cli \
  --visibility ADMIN tests/fixtures/rag-visibility/admin-policy.md
```

这三次导入不要使用 `--rebuild`。`--rebuild` 是全表替换操作，适合更换 embedding 模型后一次性重建，不适合逐个追加不同权限范围的文档。

本地角色账号和密码只用于开发验收，见 `packages/database/README.md`。客户端不提交 visibility；RAG API 根据数据库角色决定范围。

## 7. 测试替身和验证

- 认证路由使用 Fake 数据库连接和 Mock 密码校验，不调用外部身份服务。
- RAG 路由使用 Fake embedding、Fake role engine 和 Fake Redis，验证角色范围、错误脱敏和缓存 key 隔离。
- refresh rotation 使用锁定和重复请求测试验证幂等边界。
- 订单、退款、聊天、Checkpoint 和任务回归继续使用各自的 Fake/Mock；不会因为 V0.8 测试调用真实 OpenAI、支付或 Redis。
- 已运行相关 Pytest、Ruff 和变更 Python 文件 Mypy；未启动 FastAPI、Docker、Worker 或真实外部服务。

## 本版边界与后续

当前知识文档是公共知识，只按角色可见性过滤，没有用户级或租户级归属。下一步若需要租户文档，应增加明确的 tenant 归属和数据库约束，而不是只扩展 visibility 字符串。

当前 refresh token 已支持撤销和轮换；设备管理、token family、密钥轮换和外部 IdP 不在本版范围。Redis 仍不是订单、退款、Checkpoint 或权限事实来源。
