# V0.3 后端学习笔记：LangGraph 状态与 Checkpoint

## 本版结果

V0.3 在原有聊天接口上增加了可恢复的多轮状态：

```json
{
  "message": "继续刚才的问题",
  "thread_id": "thread-demo-1",
  "request_id": "request-demo-2"
}
```

- `thread_id` 定位一段对话及其 PostgreSQL checkpoint。
- `request_id` 标识 thread 内的一次请求，用于重试幂等。
- 不传 `thread_id` 时继续使用 V0.1 无状态模式。
- 同一 thread 的历史包含带角色的 `HumanMessage` 和 `AIMessage`。
- 进程退出并重新创建 Service 后，仍能从 PostgreSQL 恢复历史和幂等结果。

本版没有加入 Router、多 Agent、订单工具、JWT、SSE、RAG、退款或 Worker。

## 当前请求链

```text
POST /v1/chat
  -> ChatRequest
     -> 单字段长度与空白校验
     -> request_id / thread_id 跨字段校验
  -> chat route
  -> ChatService.reply
     -> 无 thread_id: stateless graph
     -> 有 thread_id: checkpointed graph + process-local lock
  -> LangGraph
     -> request_id 已完成: 复用原 response
     -> 新请求: normalize -> model -> 保存 messages/completed_requests
  -> AsyncPostgresSaver
  -> ChatResponse
```

## 实际演进过程

### 1. 先建立最小状态流转

第一版图只有两个节点：

```text
START -> normalize_message -> generate_response -> END
```

`SupportState` 使用 `TypedDict` 描述节点之间共享的数据。`NotRequired` 表示某个字段不会在
初始输入中出现，而是由后续节点产生；它不表示运行时会自动填默认值。

节点不直接修改传入的 `state`，而是返回本节点的更新。LangGraph 根据 State 定义合并这些
更新，再把新状态交给下一个节点。

### 2. 从字符串列表演进为角色化消息

最初的 `message_history: list[str]` 只能保存文本，无法区分用户和助手，也没有保存助手回复。
出现这个具体问题后，状态改成：

```python
messages: NotRequired[Annotated[list[AnyMessage], add_messages]]
```

`Annotated` 在这里为类型附加 reducer。`add_messages` 理解 LangChain 消息及消息 ID，可以
追加消息，也能按相同 ID 替换消息。Checkpoint 最终保存：

```text
Human(A) -> AI(A 回复) -> Human(B) -> AI(B 回复)
```

### 3. 模型边界开始接收完整历史

仅把消息存入 checkpoint 还不够。模型最初仍只接收当前的 `normalized_message`，因此恢复的
历史没有参与回答。后来 `ChatModel`、图和 OpenAI Adapter 统一改为接收：

```python
Sequence[AnyMessage]
```

使用 `Sequence` 是因为 Adapter 只需要读取消息，不应修改图维护的列表。System Prompt 每次
由 Adapter 添加，不写入 checkpoint；它属于应用配置，不属于用户对话历史。

### 4. Checkpoint 从内存迁移到 PostgreSQL

`InMemorySaver` 能证明状态恢复规则，但进程退出后数据消失。正式应用改用
`AsyncPostgresSaver`：

```text
FastAPI lifespan 启动
-> 打开 saver 异步上下文
-> await checkpointer.setup()
-> 创建 ChatService
-> yield，处理多个请求
-> 关闭 saver
-> dispose SQLAlchemy engine
```

Saver 属于应用生命周期，不会为每个请求重新连接。`setup()` 管理 LangGraph 自有的
checkpoint 表；这些表不加入 Prisma Schema。Prisma 继续只拥有 User、Order、
ShipmentEvent 等传统业务表。

### 5. 无状态和有状态调用使用两张 compiled graph

图一旦使用 checkpointer 编译，调用时就必须提供 `thread_id` 等配置。只在调用时传
`config=None` 并不能关闭 saver。为了保持 V0.1 兼容，Service 编译两张结构相同的图：

```text
stateless graph    -> 无 checkpointer
checkpointed graph -> PostgreSQL saver
```

无 `thread_id` 的调用选择第一张图，每次状态独立；有 `thread_id` 的调用选择第二张图。

### 6. request_id 与幂等分支

客户端可能在服务端已完成请求但响应丢失后重试。如果每次重试都调用模型，会产生重复消息和
额外费用。因此 checkpoint 保存：

```python
completed_requests: dict[str, str]
```

START 处的条件边先判断当前 request ID：

```text
未完成 -> normalize -> model -> 保存 response
已完成 -> reuse_completed_response -> END
```

同一 `thread_id + request_id` 的顺序重试和重叠重试都只调用模型一次。相同 request ID 在
不同 thread 中仍是两次独立请求。

`request_id` 没有 `thread_id` 就没有 checkpoint 作用域，因此 Pydantic 的
`model_validator(mode="after")` 会拒绝这种组合并返回 `422`。

### 7. 失败重试不能污染历史

模型返回空文本时，第一次实现会先保存空 `AIMessage`，Service 随后才报错。重试时模型看到：

```text
Human(A) -> AI(空) -> Human(A)
```

修复后，带 request ID 的 HumanMessage 使用稳定消息 ID。相同请求重试时，`add_messages`
替换原 HumanMessage；空响应不写入 AI 消息，也不进入 `completed_requests`。下一次成功重试
得到干净的：

```text
Human(A) -> AI(成功回复)
```

## 并发范围与不变量

两个请求同时写同一 thread 时，如果都从旧 checkpoint 恢复，可能产生分叉或覆盖：

```text
A 恢复 v1 -> 调模型
B 也恢复 v1 -> 调模型
A 保存 v2
B 保存另一个 v2
```

当前 `ChatService` 使用应用实例上的 `asyncio.Lock`：

```text
A 持锁 -> 恢复、执行、保存 -> 释放
B 等待 -> 恢复 A 的新状态 -> 执行或复用
```

当前不变量：同一 Python 进程中，checkpointed graph 的调用按顺序执行。无状态图没有共享
持久状态，可以并发执行。

这把锁目前会让不同 thread 也排队，并且不能协调多个 Python Worker。V0.3 以单 Worker
运行；多 Worker 的数据库级并发控制、租约或任务队列属于后续可靠性版本。

## 作用域区分

| 作用域 | 当前对象或数据 | 生命周期 |
|---|---|---|
| 应用/进程 | ChatService、两张 compiled graph、`asyncio.Lock` | lifespan |
| 请求 | `initial_state`、当前 message/request ID | 单次 HTTP 请求 |
| 客户端会话 | `thread_id` | 由客户端延续 |
| 持久共享 | messages、completed_requests、checkpoint 版本 | PostgreSQL |

`thread_id` 不是用户身份。V0.3 仍是匿名/demo 范围，不能用 thread ID 读取订单，也不能把它
当作授权依据。V0.4 接入 JWT 后，checkpoint 必须同时受可信 `user_id` 约束。

- Service tests：无状态兼容、顺序恢复、并发顺序、幂等与失败重试。
- Route/Schema tests：ID 去空白、长度、组合校验与参数转发。

## 本版遇到的典型错误

- `await generate_reply(...).strip()` 会先对 coroutine 调用 `strip`；拆成 await 与字符串处理
  两行最清楚。
- State 删除 `normalized_message` 后，下一个节点读取时出现 `KeyError`。
- 输入省略 `request_id` 不会清除 checkpoint 旧值；必须显式写入 `None`。
- PostgreSQL saver 已打开，但 Service 仍误传 `InMemorySaver()`，形成“连接了却没使用”。
- `reply()` 改为两张图后，构造函数忘记创建对应属性，Mypy 提前发现。
- 条件分支加入后误删新请求分支的显式 `-> END`。
- macOS 没有系统 `libpq`，基础 psycopg 无法导入；锁定 binary wheel 后解决。
- 旧测试继续断言 InMemorySaver，一度掩盖 PostgreSQL 没有真正装配。

## 当前限制

- `completed_requests` 暂不清理，长会话需要在后续版本增加保留策略。
- 同一个 request ID 搭配不同 message 时会复用第一次结果；客户端必须为不同操作生成新 ID。
- `setup()` 当前在应用启动时执行；正式部署后可根据数据库权限拆成独立部署步骤。
- 进程在模型已经产生费用、但成功 checkpoint 尚未提交前崩溃，重试仍可能再次调用模型；
  外部模型调用无法仅靠本地状态获得严格 exactly-once。
- 未进行本轮真实 OpenAI 在线 smoke test；自动化验证全部使用 Fake/Mock。

## 可手动尝试

1. 使用相同 `thread_id`、不同 `request_id` 连续提问，观察第二次回答能引用第一次上下文。
2. 使用相同 `thread_id + request_id` 重试，确认返回第一次的相同内容。
3. 重启 Agent Core 后继续同一 thread，确认 PostgreSQL 恢复历史。
4. 不传 thread ID 发起两次请求，确认两次保持无状态。

手动测试时每次新操作应生成新的 request ID。正式认证进入 V0.4 前，不要把 thread ID 当作
敏感数据访问凭据。
