# V0.2 后端学习笔记：订单数据库与异步查询

## 本版结果

V0.2 增加只读订单详情接口：

```text
GET /v1/orders/{order_id}
```

它返回当前 demo 用户自己的订单基本信息、精确金额和按发生时间升序排列的物流轨迹。
他人的订单与不存在的订单统一返回 `404`。V0.1 的聊天接口保持不变。

本版没有订单写入、库存、退款、LangGraph、工具调用、SSE、RAG 或正式认证。

## 实际演进过程

这次没有先创建最终目录，而是从一个文件中的可观察行为开始。

### 1. 内存订单先固定业务规则

第一版使用两个内存订单，先证明三个行为：

- `demo-user-li` 可以读取自己的 `order-demo-001`；
- `order-demo-002` 属于其他用户，对当前用户不可见；
- 他人订单与不存在订单返回相同的 `404`。

此时共享字典只读，所以并发请求不会互相覆盖数据。但它只属于单个 Python 进程，重启后
恢复，多个进程也不能共享，因此持久数据库成为真实需要。

### 2. Prisma 成为业务表的唯一 migration owner

`packages/database` 定义并迁移传统关系数据：

```text
User 1 ── N Order 1 ── N ShipmentEvent
```

Prisma 负责：

- schema 与外键；
- PostgreSQL enum、索引和 `NUMERIC(12, 2)`；
- 两份版本化 migration；
- 可重复运行的中文 demo seed。

SQLAlchemy 只读取这些表，不调用 `metadata.create_all()`，也不为它们建立 Alembic
migration。同一张表只能有一个 schema owner，否则两个迁移系统会互相争夺结构状态。

物流 seed 故意不按时间顺序写入。API 的顺序来自 SQL：

```sql
ORDER BY occurred_at ASC, id ASC
```

`id` 是相同时间下的稳定次级排序，避免结果顺序随查询计划变化。

### 3. 先用 AsyncEngine connection，不提前加 Session

订单路由最初只有一条只读 SQL，因此直接从现有 `AsyncEngine` 连接池借 connection：

```python
async with engine.connect() as connection:
    result = await connection.execute(statement, parameters)
```

这里没有 ORM 实体跟踪、写入事务或多个对象的生命周期管理，`AsyncSession` 暂时不会解决
新的问题。等后续出现 ORM 映射、事务写入或需要统一提交/回滚时，再引入 Session 才有明确
收益。

Engine 属于应用实例并共享连接池；connection 属于单次请求：

```text
请求 A -> 借 connection A -> 两次只读查询 -> 归还
请求 B -> 借 connection B -> 两次只读查询 -> 归还
```

本版没有订单写入，因此没有读写竞争，不增加锁或更高事务隔离级别。

### 4. Python 变量存在，不代表资源仍有效

开发中曾把第二次查询写在 `async with` 外。离开区块后，`connection` 变量仍能被 Python
访问，但底层连接已经归还连接池。Ruff 和 Mypy 无法检测这种资源生命周期错误。

最终两次数据库操作都位于同一个 `async with` 内，而 `.all()` 读取出的 Python 列表可以
在区块外继续使用。

### 5. 返回字典变复杂后才引入 Pydantic

最初返回类型是：

```python
dict[str, str | Decimal | datetime]
```

它不能表达某个 key 对应哪个类型，也不能声明六个字段必须存在。测试 Fake 缺少
`order_number` 时，只在运行期出现 `KeyError`。

因此才增加 `OrderDetailResponse` 和 `ShipmentEventResponse`。`NUMERIC(12, 2)` 由
asyncpg/SQLAlchemy 读取为 Python `Decimal`，FastAPI 输出为 JSON 字符串；PostgreSQL
`TIMESTAMPTZ` 对应带时区时间，并由 `AwareDatetime` 验证。

模型目前留在订单路由文件，因为只有这一个端点使用。出现第二个消费者或文件继续膨胀
时，再移动到 `schemas/`。

### 6. 测试变复杂后才抽取 dependency

当路由同时包含两条 SQL、结果映射和 HTTP `404` 后，Route 测试必须模拟：

```text
connect -> execute -> mappings -> one_or_none/all
```

这使 HTTP 测试与 SQLAlchemy 细节绑定。因此把数据库读取抽成同文件中的
`load_owned_order` dependency：

```text
get_order            -> HTTP 404 与响应
load_owned_order     -> SQL、归属过滤、结果转换
```

Route 测试现在通过 `dependency_overrides` 注入结果；loader 测试才需要 Fake connection。
这已经是当前功能需要的最小数据访问边界。

当前没有额外 Service、Repository class 或 Protocol，因为没有独立业务计算，也没有第二种
数据实现。此时增加它们只会逐层转发相同参数。

## 临时身份边界

当前身份来自服务端配置：

```dotenv
DEMO_USER_ID=demo-user-li
```

`get_demo_user_id()` 不读取客户端 header、query 或 path。SQL 在数据库中同时过滤：

```sql
WHERE id = :order_id
  AND user_id = :user_id
```

因此调用方不能仅凭订单 ID 读取其他用户订单，也不能伪造 `X-Demo-User-Id` 切换身份。
正式认证到来时，用 JWT claims 替换这个 dependency，订单查询仍接收同一个 `user_id`。

这只是清晰的 demo 边界，不等于正式认证或授权系统。

## 数据库错误边界

loader 只捕获 `SQLAlchemyError`：

```text
SQLAlchemyError -> 503 / 订单服务暂时不可用，请稍后重试。
```

日志仅记录异常类名，不记录原始异常文本、SQL 参数、数据库 URL 或密码。普通 Python 编程
错误不会被宽泛的 `except Exception` 伪装成数据库故障。

## 当前请求链

```text
GET /v1/orders/{order_id}
  -> get_demo_user_id（服务端临时身份）
  -> load_owned_order
     -> AsyncEngine 连接池
     -> 按 order_id + user_id 查询订单
     -> 按 occurred_at + id 查询物流
     -> Pydantic response models
  -> get_order
     -> None: 404
     -> OrderDetailResponse: 200
```

## 测试层次

- Route tests：HTTPX ASGI Transport + dependency override。
- Loader tests：Fake Engine/Connection，验证 SQL 参数、查询次数和排序语句。
- Failure test：Fake 数据库异常，验证 `503` 及响应/日志脱敏。
- Integration test：独立 `ecommerce_agents_test` 数据库，验证真实 migration、seed、
  `Decimal`、物流排序和归属过滤。
- V0.1 regression：聊天测试继续使用 Fake/Mock，不调用 OpenAI。

Integration test 默认跳过，只有显式提供 `TEST_DATABASE_URL` 时才运行，日常单元测试不依赖
Docker。

## 本版遇到的典型错误

- 替换内存数据后忘记删除旧字典，形成两套看似有效的数据来源。
- 测试直接连接尚未创建的 `ecommerce_agents_test`，说明单元测试缺少数据库替身。
- Fake Row 没同步新增字段或 `.all()`，说明测试曾与 SQLAlchemy 链条耦合过紧。
- connection 变量在 `async with` 外仍存在，但底层资源已经关闭。
- `str(SQLAlchemy URL)` 会把密码渲染成 `***`；真实子进程连接必须显式使用
  `render_as_string(hide_password=False)`，同时禁止输出该值。
