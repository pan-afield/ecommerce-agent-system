# V0.6 后端学习记录：企业知识库 RAG 基础

## 本版边界

本版完成一条可观察、可重复执行的本地知识库链：企业政策文本或 PDF 可以被稳定切片，切片保留来源和页码，由本地 `BAAI/bge-m3` 生成 embedding 并写入 pgvector；查询同时走语义检索和关键词检索，最后返回稳定排序和可追踪引用。OpenAI-compatible API 只服务聊天模型，不再参与 RAG embedding。

本版没有加入完整 LangGraph RAG Agent、Worker、后台 ingestion、全文 `tsvector`、复杂权限、真实文档服务或自动化真实 OpenAI 调用。

## 实际数据流

```text
CLI file paths (.txt / .md / .pdf)
  -> LlamaIndex Document / pypdf page extraction
  -> chunk_policy_text() / chunk_pdf_document()
  -> KnowledgeChunk(source_id, page_number, chunk_index, chunk_id)
  -> LocalEmbeddingsAdapter            [LlamaIndex -> LangChain interface]
  -> embed_knowledge_chunks()          [async local embedding]
  -> EmbeddedKnowledgeChunk
  -> incremental store or atomic rebuild
  -> agent_core.knowledge_chunks       [pgvector + embedding_model]

user query
  -> retrieve_knowledge()
  -> aembed_query(query)
  -> semantic search (<=>)
  -> keyword search (strpos)
  -> candidate qualification (raw distance + usable content)
  -> fuse_search_results()              [RRF]
  -> build_knowledge_citations()
  -> GET /v1/rag/search 或 POST /v1/chat
```

`GET /v1/rag/search` 目前是明确触发的只读 API；它复用 V0.4 的 JWT 身份依赖，模型不会自行调用它，也不会在本版生成最终客服回答。

## Python 学习点

### dataclass 与不可变结果

`KnowledgeChunk`、`EmbeddedKnowledgeChunk`、`SemanticSearchResult`、`HybridSearchResult` 和 `KnowledgeCitation` 使用 `@dataclass(frozen=True)` 表示一次处理结果。`frozen=True` 不能阻止列表内容被修改，但可以防止调用方替换字段，足以表达“本次流水线结果不应被悄悄改写”。

LlamaIndex `Document` 位于文件内容进入切片算法的边界：文本文件把正文和 `source_id` 放入 `Document`；PDF 每个非空页面分别建立 `Document`，并在 metadata 中保留 `page_number`。项目仍使用自己的 `KnowledgeChunk` 生成稳定 `chunk_id`，没有把来源身份交给第三方库隐式决定。

### 类型标注不是运行时校验

`list[KnowledgeChunk]` 帮助 Mypy 检查调用关系；它不会自动拒绝错误数据。`page_number`、`limit`、embedding 维度等运行时约束仍由函数显式检查，API 参数则由 FastAPI/Pydantic 检查。

### async/await 与外部模型

embedding 边界调用 `await embeddings.aembed_documents(...)` 和 `await embeddings.aembed_query(...)`。异步路由不能直接调用同步模型推理，否则一次较慢的 CPU 推理会阻塞事件循环。`LocalEmbeddingsAdapter` 把 LlamaIndex 的异步 HuggingFace 方法适配成现有 LangChain `Embeddings` 接口，文本处理和检索函数因此仍可注入 Fake，自动测试不会下载真实模型。

### 在重复真实出现后抽取 helper

非流式和流式 chat 都需要读取 embedding、构建上下文并处理 `ValueError`。这段逻辑重复出现后，修改一处可能漏掉另一处，因此在同一个路由文件中抽取了 `_build_chat_rag_prompt()`。它返回请求局部的 `tuple[str | None, list[KnowledgeCitation]]`，让 chat 响应可以复用同一次检索的引用；它不把 prompt 或 citations 写入 `app.state`，也没有提前创建新的 service 或 repository 层。

引用到 API 响应的字段映射随后在 chat 和 RAG 两个路由中重复出现，于是抽取了 `app/api/serializers.py` 中的纯函数 `format_citations()`。它只把领域对象转换成 `KnowledgeCitationResponse`，不读取请求状态，也不改变原始引用；SSE 需要发送 JSON 时再对返回模型调用 `model_dump(mode="json")`。

### 配置与资源生命周期

RAG embedding 不再读取 `OPENAI_API_KEY` 或 `OPENAI_EMBEDDING_MODEL`。配置契约改为 `RAG_EMBEDDING_MODEL`（默认 `BAAI/bge-m3`）、`RAG_EMBEDDING_DIMENSIONS`（默认 `1024`）、可选的 `RAG_EMBEDDING_CACHE_DIR` 和 `RAG_EMBEDDING_DEVICE`（默认 `cpu`）。本版依赖 `llama-index-core`、`llama-index-embeddings-huggingface` 和 `sentence-transformers`；`local_embeddings.py` 只负责把配置映射成 `HuggingFaceEmbedding` 构造参数，不在导入时下载或加载模型。

LlamaIndex 的 embedding API 与现有检索代码使用的 LangChain `Embeddings` API 不同，因此 `LocalEmbeddingsAdapter` 只在这个边界做方法名转换。同步方法满足抽象接口，实际 RAG 请求使用 `aget_text_embedding_batch()` 和 `aget_query_embedding()`，不会在异步路由中退回同步调用。第三方包没有完整类型存根，适配边界用精确 `cast` 固定项目所需的向量类型。

OpenAI 聊天服务和本地 RAG embedding 是两个独立的进程级资源：即使 `OPENAI_API_KEY` 缺失，也不应阻止本地 embedding 初始化。`main.py` 现在在 OpenAI key 判断之前创建本地 embedding；没有聊天配置时只跳过 ChatService。两个并发请求都只读取同一个已加载的进程级 embedding 对象，各自的 query 和结果列表仍属于请求作用域，不共享可变查询状态。

### 第三方类型声明

`llama-index-embeddings-huggingface` 和 `pgvector` 当前没有提供项目所需的完整类型存根，因此只在对应第三方导入处使用精确的 `# type: ignore[import-untyped]`。适配器内部再用 `cast` 把第三方返回值收窄成 `list[float]` 或 `list[list[float]]`，其后的项目代码不继续传播 `Any`。

## 切片与来源追踪

`chunk_policy_text()` 先统一换行，再按空行分段，长段落按 800 字符切开。`chunk_id` 是由 `source_id`、页码（如有）、chunk index 和内容计算出的 SHA-256。相同文档重复导入会得到相同 ID；同一内容位于不同页时，页码参与哈希，避免来源碰撞。

Markdown 标题与紧随其后的正文会在切片前合并，因此标题不会单独进入向量库。已有旧数据不会自动改变，切片规则调整后必须执行一次 `--rebuild`；本次 smoke fixture 从旧的 8 个 chunk 重建为 4 个“标题 + 正文”chunk。

PDF 使用 `pypdf.PdfReader` 提取页面文本。空白页跳过，但保留原始页码；因此引用中的 `page_number` 是 PDF 页码，而不是“非空页面序号”。

## PostgreSQL、Prisma 与 SQLAlchemy 边界

传统业务表仍由 Prisma 管理。RAG 表由 Agent Core migration 管理，并放在独立的 `agent_core` schema。migration 先启用 `vector` 扩展，再建立 `embedding vector(1024)`；本版没有提前建立 HNSW/IVFFlat 索引，因为还没有证明查询规模需要索引。

SQLAlchemy async 只执行查询和写入，不创建这些表。写入使用 `engine.begin()`；语义和关键词检索使用 `engine.connect()`。`Vector(1024)` 是 SQL 参数的数据库类型，真正发送的值仍是 Python `list[float]`。Python 侧的 `EMBEDDING_DIMENSIONS` 与 migration 的列维度必须保持同一个契约。

查询前会从 PostgreSQL `pg_attribute.atttypmod` 读取真实列维度；不是 1024 时抛出 `RagVectorDimensionError`，不会等到距离运算才得到难诊断的数据库异常。每行同时保存 `embedding_model`，查询只命中当前配置模型生成的向量。

模型名称或维度改变后必须用 `--rebuild` 重新生成全部向量。不能只修改 `.env` 后继续查询旧数据；未来若要同时保留多个语言模型，应拆分 collection 或表，而不是把不同模型写入同一张表。

## 幂等、原子性与并发

### 重复导入

两个导入任务同时写同一个 `chunk_id`：

```text
A: INSERT ... ON CONFLICT DO NOTHING -> RETURNING chunk_id -> True
B: INSERT 同一个 ID                  -> 无返回行          -> False
```

主键保证每个 chunk 最多一行。当前约定 `source_id` 是不可变文档版本；内容变化使用新版本 ID，不在本版原地覆盖旧向量。

### 批量事务

如果任务 A 依次写入三个 chunk，第二个失败：

```text
A: chunk 1 执行成功
A: chunk 2 数据库异常
A: engine.begin() 退出 -> 整个事务回滚
```

因此不会留下半份文档。批量函数不会调用单条函数，因为单条函数会为每一行创建独立事务。

### 模型切换与原子 rebuild

`replace_all_embedded_knowledge_chunks()` 在同一个事务里先删除旧知识，再写入整批新知识。新批次任意一行失败时，删除和此前插入都会一起回滚，旧模型数据仍完整可查。

增量导入和全量 rebuild 都先取得同一个 PostgreSQL transaction advisory lock：

```text
A: 取得 lock -> 读取空模型集合 -> 写入 model-a -> COMMIT
B: 等待 lock -> A 提交后才读取 -> 发现 model-a 与 model-b 冲突 -> ROLLBACK
```

不变量不是“A 必须获胜”，而是“表内最多存在一个 embedding model”。锁只保护模型检查与写入这一小段事务，不限制只读查询。

### 查询并发

两个查询请求各自得到局部 query、向量、结果列表和数据库连接；它们不共享可变 Python 状态，也不修改 durable state，因此当前不需要锁。数据库连接由 SQLAlchemy pool 按请求借用和归还。chat 路由的并发测试同时发送两个不同 query，确认各自的 prompt 和 citations 不会串到另一个请求。

## 检索与引用

语义检索使用 pgvector 的余弦距离 `<=>`，距离越小越相近；关键词检索使用 PostgreSQL 精确子串匹配。两种原始分数不可直接相加，因此 `fuse_search_results()` 使用 Reciprocal Rank Fusion：第 `rank` 名贡献 `1 / (60 + rank)`。同一 `chunk_id` 双路命中只保留一次，最终按分数降序、ID 升序排序。

RRF 分数只表达“候选在两条排名列表中的位置”，不是相似度百分比，也不适合用固定阈值判断无结果。融合前的资格判断使用可解释的原始证据：语义候选必须通过当前 fixture 校准的最大距离 `0.30`，关键词候选必须有精确匹配；两路都排除只有 Markdown 标题的内容。这样“苹果”的高距离候选会变成空结果，而“退款政策”的正文仍能保留。`score` 字段继续表示 RRF 融合分，API 没有改名或改变类型。

`KnowledgeCitation` 只复制来源字段和融合分数，不摘要、不改写内容。这样前端或后续回答可以明确显示 `source_id`、`chunk_id` 和页码。`format_knowledge_citations()` 再把结构化引用转换成稳定的中文证据块，保留编号、来源、页码、chunk ID 和原文，供未来模型提示词使用。

`build_rag_prompt()` 是下一层纯文本边界：有证据时明确告诉模型只能依据证据回答，证据不足时要承认无法确认；无证据时仍保留用户问题。它不创建消息对象，也不调用模型，因此可以独立测试。

`normalize_message()` 同时处理原始问题清理和模型消息选择后，抽出了同文件中的 `select_model_message()` 纯函数。它只根据“非空 RAG prompt 优先，否则使用原始问题”返回字符串，不了解 LangGraph、HTTP 或数据库；参数化测试固定了 `None`、空字符串和非空 prompt 三种边界。

`POST /v1/chat` 和 `POST /v1/chat/stream` 在 embedding client 已配置时，都会先构造 `RagContext` 和 prompt，再把 prompt 作为可选参数交给 `ChatService`；没有 embedding 时继续走 V0.5 原来的问答路径。流式接口仍发送原有的 `assistant` 和 `done` 两个 SSE 事件，但 `assistant` 的 JSON data 现在也包含 `citations` 数组；RAG 检索发生在开始发送事件之前。

非流式 `/v1/chat` 还会把同一次检索得到的 `KnowledgeCitation` 映射为共享的 `KnowledgeCitationResponse` 返回给前端，因此前端不需要为了显示引用再发起第二次检索。`/v1/rag/search` 也复用这个响应模型，避免两个 API 的字段定义漂移。`ChatResponse.citations` 始终是列表；Pydantic 的 `Field(default_factory=list)` 确保每个响应拥有自己的空列表。

当 prompt 开始接入 LangGraph 时，`SupportState.normalized_message` 仍只保存清理后的原始用户问题，供 `route_intent()` 判断；可选的 `rag_prompt` 只决定发给模型的 `HumanMessage` 内容。这个分离避免证据正文中的“订单”等词改变业务路由。

## 可重复 ingestion 入口

`python -m app.rag.ingestion_cli` 接受一个或多个 `.txt`、`.md`、`.pdf` 路径。默认模式按稳定 `chunk_id` 增量写入，重复执行返回 0 个新增块；`--rebuild` 用当前配置模型重新生成并原子替换全部知识块。CLI 在 `finally` 中释放数据库 engine，即使 embedding 或写入失败也不会遗留连接池。

文档入库和查询都从同一个 `Settings.rag_embedding_model` 取得模型身份。CLI 不属于常驻 Worker，每次命令运行完成即退出；后台任务、上传 API 和大文档队列留给后续版本。

## HTTP 边界

`/v1/rag/search` 的路由只负责 JWT 身份检查、读取 app state、调用 `build_rag_context()` 和转换 Pydantic 响应模型。请求顺序是：没有 token 先返回 `401`；已认证但 query 超过 500 个字符时由 FastAPI 返回 `422`；`limit` 不在 1～10 时也由 FastAPI 在进入 service 前返回 `422`；embedding 未初始化返回 `rag_not_configured`；本地模型推理失败返回 `rag_embedding_unavailable` 503；数据库向量列维度不兼容返回 `rag_database_incompatible` 503；其他未知数据库异常仍保持标准 `500`。所有预期错误都使用稳定、脱敏的客户端文案。

普通 chat 和 SSE 共用 `_build_chat_rag_prompt()`，因此 embedding 失败和数据库维度错误在两条路径上采用相同的 503 行为，并且在调用聊天模型前短路，避免产生无意义费用。

chat 和 RAG 现在共享 `ApiErrorCode` 联合类型与 `ErrorResponse` 结构。类型名称不再局限于 chat，但错误码字符串保持稳定；这让前端可以按同一个 `error.code` 分支处理两个 API。

两个 chat 路由的 OpenAPI 声明也明确列出 RAG 可能产生的 422 `ErrorResponse`。声明不会改变运行时逻辑，但会让生成的接口文档与真实错误结构一致。

## 自动化验证

纯单元和路由测试使用 Fake Embeddings、Fake Engine、monkeypatch 和 HTTPX ASGI Transport，不调用真实 OpenAI、不下载 HuggingFace 模型。中英文 query 都会通过同一条异步 embedding、语义检索、关键词检索和融合链。生命周期测试还固定了 `OPENAI_API_KEY=None` 时 RAG 仍能独立初始化。

本轮最终验证：

```text
366 passed（包含 8 个隔离 PostgreSQL 集成测试）
Ruff passed（app + tests）
Mypy strict passed（33 个变更或新增 Python 文件）
```

覆盖内容包括 RAG route、普通 chat、SSE、中英文检索、无关查询空结果、标题过滤、本地模型独立生命周期，以及隔离 PostgreSQL 中的 1024 维列、vector round-trip、重复导入、批量回滚、原子 rebuild 回滚和并发模型互斥。订单、退款和 checkpoint 集成回归也使用同一个隔离测试库通过。

## 人工验收结果

用户在 Cursor 中完成真实 `BAAI/bge-m3` smoke test：

- `OPENAI_API_KEY` 为空时，应用成功启动；`/health/ready` 报告 `database=ok`、`rag_embeddings=ok`、`openai_chat=unavailable`。
- 双语 Markdown fixture 在质量修复前首次导入写入 8 个知识块；切片规则更新后执行 `--rebuild`，得到 4 个标题与正文合并的知识块。相同版本再次增量导入写入 0 个，真实数据库幂等通过。
- 中文查询“退款政策”返回包含实际退款正文的 citation，不再返回独立标题。
- 英文查询“return policy”返回包含英文退款正文的 citation，真实多语言检索通过。
- 无关查询“苹果”返回 `200 + citations: []`，前端可以进入无结果状态。
- API 全程使用本地 embedding；没有配置或调用 OpenAI Embeddings API。

## 手动练习

1. 在测试中把两个语义结果的 `distance` 改成相反的数值，观察 RRF 排名为什么仍由输入名次决定。
2. 为关键词检索增加一个相同匹配位置、不同 `chunk_id` 的行，验证稳定排序的最后一个排序键。
3. 在隔离 PostgreSQL 中应用 migration，插入一个 1024 维向量，再尝试插入 3 维向量，观察数据库如何保护列维度不变量。不要对开发库执行破坏性操作。
4. 在 Cursor 的本地 `.env` 设置 `RAG_EMBEDDING_MODEL`、`RAG_EMBEDDING_DIMENSIONS=1024`、`RAG_EMBEDDING_CACHE_DIR` 和 `RAG_EMBEDDING_DEVICE=cpu`。OpenAI 配置只服务聊天模型；真实模型下载和在线调用属于手动 smoke test，不属于自动化验证。
5. 准备一份不含私有资料的小型政策文件，运行 `python -m app.rag.ingestion_cli path/to/policy.md --rebuild`，再手动调用 `/v1/rag/search?query=退款政策&limit=3` 检查 citations。模型首次运行可能需要下载，必须由用户在 Cursor 中主动执行。

## 版本边界

- 本版没有增加独立的 LangGraph RAG Agent 节点；现有 chat graph 接收检索得到的 RAG prompt，普通 chat 和 SSE 都返回 citations。
- pgvector 集成测试使用 `ecommerce_agents_test` 隔离数据库运行；本轮没有启动 Docker，也没有触碰开发库。
- 尚未加入向量索引、全文索引、文档版本替换、后台 ingestion 或权限控制。
- 自动测试仍不会下载或运行真实模型；真实 `BAAI/bge-m3` 结果来自用户在 Cursor 中完成的独立人工验收。
