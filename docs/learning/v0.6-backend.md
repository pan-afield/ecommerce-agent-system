# V0.6 后端学习记录：企业知识库 RAG 基础

## 本版边界

本版先完成一条可观察的知识库检索链：企业政策文本可以被稳定切片，切片可以保存来源和页码，文本可以生成 embedding 并写入 pgvector，查询可以同时走语义检索和关键词检索，最后返回稳定排序和可追踪引用。

本版没有加入完整 LangGraph RAG Agent、Worker、后台 ingestion、全文 `tsvector`、复杂权限、真实文档服务或自动化真实 OpenAI 调用。

## 实际数据流

```text
PDF bytes / policy text
  -> chunk_policy_text() / chunk_pdf_document()
  -> KnowledgeChunk(source_id, page_number, chunk_index, chunk_id)
  -> embed_knowledge_chunks()          [async embedding interface]
  -> EmbeddedKnowledgeChunk
  -> store_embedded_knowledge_chunks() [one transaction, pgvector]

user query
  -> retrieve_knowledge()
  -> aembed_query(query)
  -> semantic search (<=>)
  -> keyword search (strpos)
  -> fuse_search_results()              [RRF]
  -> build_knowledge_citations()
  -> GET /v1/rag/search 或 POST /v1/chat
```

`GET /v1/rag/search` 目前是明确触发的只读 API；它复用 V0.4 的 JWT 身份依赖，模型不会自行调用它，也不会在本版生成最终客服回答。

## Python 学习点

### dataclass 与不可变结果

`KnowledgeChunk`、`EmbeddedKnowledgeChunk`、`SemanticSearchResult`、`HybridSearchResult` 和 `KnowledgeCitation` 使用 `@dataclass(frozen=True)` 表示一次处理结果。`frozen=True` 不能阻止列表内容被修改，但可以防止调用方替换字段，足以表达“本次流水线结果不应被悄悄改写”。

### 类型标注不是运行时校验

`list[KnowledgeChunk]` 帮助 Mypy 检查调用关系；它不会自动拒绝错误数据。`page_number`、`limit`、embedding 维度等运行时约束仍由函数显式检查，API 参数则由 FastAPI/Pydantic 检查。

### async/await 与外部模型

embedding 边界调用 `await embeddings.aembed_documents(...)` 和 `await embeddings.aembed_query(...)`。异步路由不能调用同步 embedding 方法，否则一个慢的外部请求会阻塞事件循环。真实 `OpenAIEmbeddings` 在 `openai_embeddings.py` 构造，文本处理函数只依赖 LangChain 的 `Embeddings` 接口，因此 Fake 可以替换它。

### 在重复真实出现后抽取 helper

非流式和流式 chat 都需要读取 embedding、构建上下文并处理 `ValueError`。这段逻辑重复出现后，修改一处可能漏掉另一处，因此在同一个路由文件中抽取了 `_build_chat_rag_prompt()`。它返回请求局部的 `tuple[str | None, list[KnowledgeCitation]]`，让 chat 响应可以复用同一次检索的引用；它不把 prompt 或 citations 写入 `app.state`，也没有提前创建新的 service 或 repository 层。

引用到 API 响应的字段映射随后在 chat 和 RAG 两个路由中重复出现，于是抽取了 `app/api/serializers.py` 中的纯函数 `format_citations()`。它只把领域对象转换成 `KnowledgeCitationResponse`，不读取请求状态，也不改变原始引用；SSE 需要发送 JSON 时再对返回模型调用 `model_dump(mode="json")`。

### 配置与资源生命周期

`Settings.openai_embedding_model` 从 `OPENAI_EMBEDDING_MODEL` 读取，默认是 `text-embedding-3-small`。`main.py` 在应用 lifespan 中创建一次 `rag_embeddings`；请求只读取 app state，不为每个请求重新创建客户端。没有 API key 时 state 是 `None`，路由返回 `503`，而不是让 `AttributeError` 变成 `500`。

### 第三方类型声明

`langchain-openai` 的 `OpenAIEmbeddings` 使用了 Pydantic 字段别名。当前版本的 Mypy 需要 `openai_api_key`、`openai_api_base` 和 `request_timeout` 这些字段名。`pgvector` 没有提供类型存根，因此只对该导入使用精确的 `# type: ignore[import-untyped]`。

## 切片与来源追踪

`chunk_policy_text()` 先统一换行，再按空行分段，长段落按 800 字符切开。`chunk_id` 是由 `source_id`、页码（如有）、chunk index 和内容计算出的 SHA-256。相同文档重复导入会得到相同 ID；同一内容位于不同页时，页码参与哈希，避免来源碰撞。

PDF 使用 `pypdf.PdfReader` 提取页面文本。空白页跳过，但保留原始页码；因此引用中的 `page_number` 是 PDF 页码，而不是“非空页面序号”。

## PostgreSQL、Prisma 与 SQLAlchemy 边界

传统业务表仍由 Prisma 管理。RAG 表由 Agent Core migration 管理，并放在独立的 `agent_core` schema。migration 先启用 `vector` 扩展，再建立 `embedding vector(1536)`；本版没有提前建立 HNSW/IVFFlat 索引，因为还没有证明查询规模需要索引。

SQLAlchemy async 只执行查询和写入，不创建这些表。写入使用 `engine.begin()`；语义和关键词检索使用 `engine.connect()`。`Vector(1536)` 是 SQL 参数的数据库类型，真正发送的值仍是 Python `list[float]`。

## 幂等、原子性与并发

### 重复导入

两个导入任务同时写同一个 `chunk_id`：

```text
A: INSERT ... ON CONFLICT DO NOTHING -> RETURNING chunk_id -> True
B: INSERT 同一个 ID                  -> 无返回行          -> False
```

主键保证每个 chunk 最多一行。当前约定 `source_id` 是不可变文档版本；内容变化使用新版本 ID，不在本版原地覆盖旧向量。

### 批量事务

如果任务 A 依次写入三个 chunk，第二个失败：

```text
A: chunk 1 执行成功
A: chunk 2 数据库异常
A: engine.begin() 退出 -> 整个事务回滚
```

因此不会留下半份文档。批量函数不会调用单条函数，因为单条函数会为每一行创建独立事务。

### 查询并发

两个查询请求各自得到局部 query、向量、结果列表和数据库连接；它们不共享可变 Python 状态，也不修改 durable state，因此当前不需要锁。数据库连接由 SQLAlchemy pool 按请求借用和归还。chat 路由的并发测试同时发送两个不同 query，确认各自的 prompt 和 citations 不会串到另一个请求。

## 检索与引用

语义检索使用 pgvector 的余弦距离 `<=>`，距离越小越相近；关键词检索使用 PostgreSQL 精确子串匹配。两种原始分数不可直接相加，因此 `fuse_search_results()` 使用 Reciprocal Rank Fusion：第 `rank` 名贡献 `1 / (60 + rank)`。同一 `chunk_id` 双路命中只保留一次，最终按分数降序、ID 升序排序。

`KnowledgeCitation` 只复制来源字段和融合分数，不摘要、不改写内容。这样前端或后续回答可以明确显示 `source_id`、`chunk_id` 和页码。`format_knowledge_citations()` 再把结构化引用转换成稳定的中文证据块，保留编号、来源、页码、chunk ID 和原文，供未来模型提示词使用。

`build_rag_prompt()` 是下一层纯文本边界：有证据时明确告诉模型只能依据证据回答，证据不足时要承认无法确认；无证据时仍保留用户问题。它不创建消息对象，也不调用模型，因此可以独立测试。

`normalize_message()` 同时处理原始问题清理和模型消息选择后，抽出了同文件中的 `select_model_message()` 纯函数。它只根据“非空 RAG prompt 优先，否则使用原始问题”返回字符串，不了解 LangGraph、HTTP 或数据库；参数化测试固定了 `None`、空字符串和非空 prompt 三种边界。

`POST /v1/chat` 和 `POST /v1/chat/stream` 在 embedding client 已配置时，都会先构造 `RagContext` 和 prompt，再把 prompt 作为可选参数交给 `ChatService`；没有 embedding 时继续走 V0.5 原来的问答路径。流式接口仍发送原有的 `assistant` 和 `done` 两个 SSE 事件，但 `assistant` 的 JSON data 现在也包含 `citations` 数组；RAG 检索发生在开始发送事件之前。

非流式 `/v1/chat` 还会把同一次检索得到的 `KnowledgeCitation` 映射为共享的 `KnowledgeCitationResponse` 返回给前端，因此前端不需要为了显示引用再发起第二次检索。`/v1/rag/search` 也复用这个响应模型，避免两个 API 的字段定义漂移。`ChatResponse.citations` 始终是列表；Pydantic 的 `Field(default_factory=list)` 确保每个响应拥有自己的空列表。

当 prompt 开始接入 LangGraph 时，`SupportState.normalized_message` 仍只保存清理后的原始用户问题，供 `route_intent()` 判断；可选的 `rag_prompt` 只决定发给模型的 `HumanMessage` 内容。这个分离避免证据正文中的“订单”等词改变业务路由。

## HTTP 边界

`/v1/rag/search` 的路由只负责 JWT 身份检查、读取 app state、调用 `build_rag_context()` 和转换 Pydantic 响应模型。请求顺序是：没有 token 先返回 `401`；已认证但 query 超过 500 个字符时由 FastAPI 返回 `422`；`limit` 不在 1～10 时也由 FastAPI 在进入 service 前返回 `422`；embedding 未配置返回统一的 `rag_not_configured` 错误；空 query 或其他预期的 `ValueError` 返回统一的 `rag_invalid_query` 错误，不把底层异常文本返回给客户端；数据库或 pgvector 异常保持标准 `500`，也不会被伪装成成功的空结果。

chat 和 RAG 现在共享 `ApiErrorCode` 联合类型与 `ErrorResponse` 结构。类型名称不再局限于 chat，但错误码字符串保持稳定；这让前端可以按同一个 `error.code` 分支处理两个 API。

两个 chat 路由的 OpenAPI 声明也明确列出 RAG 可能产生的 422 `ErrorResponse`。声明不会改变运行时逻辑，但会让生成的接口文档与真实错误结构一致。

## 手动练习

1. 在测试中把两个语义结果的 `distance` 改成相反的数值，观察 RRF 排名为什么仍由输入名次决定。
2. 为关键词检索增加一个相同匹配位置、不同 `chunk_id` 的行，验证稳定排序的最后一个排序键。
3. 在隔离 PostgreSQL 中应用 migration，插入一个 1536 维向量，再尝试插入 3 维向量，观察数据库如何保护列维度不变量。不要对开发库执行破坏性操作。
4. 在 Cursor 的本地 `.env` 设置 `OPENAI_API_KEY`、`OPENAI_BASE_URL`（如使用兼容服务）和 `OPENAI_EMBEDDING_MODEL`，启动前端或 FastAPI 由用户自行执行；真实在线调用只属于手动 smoke test，不属于自动化验证。
