# Ecommerce Agent System 开发与学习进度计划

> 更新日期：2026-09-01

## 1. 计划基准

本项目同时承担产品实现和 Python 学习两个目标，开发方式分为：

- 前端：由 Codex 对话直接实现，用户主要负责需求确认、视觉检查和前后端联调验收。
- 后端：采用教学模式。用户亲自编写生产业务代码，Codex 每次提供一个小步骤，并负责讲解、审查、自动化测试、Mock、验证和学习文档。
- 单次学习时间：固定按 3 小时统计和安排。
- 推荐频率：每周 6 次，保留一天用于休息、复盘或处理计划外问题。

由于后端采用教学模式，整体速度会比直接代写慢约 30%～50%，但这部分时间计入 Python、FastAPI、数据库和 Agent 工程的有效学习时间。

按当前已完成内容重新估算，V0.7 预计还需要约 **36～52 个有效小时**：

- 固定 3 小时/次：约 12～18 次学习班。
- 每周 6 次时，理论投入约为 18 小时；加入教学、复盘、返工和计划外问题缓冲后，剩余阶段预计约 5～9 周。
- 当前没有连续记录每次学习班的实际用时，因此剩余工时按各版本范围估算，不用未经记录的时间制造精确进度。

## 3. 用户、会话与认证现状

项目已建立服务端 JWT 认证边界，但尚不存在正式登录/发 token 服务。三个标识不能混为一谈：

| 标识 | 当前/计划用途 | 是否是可信用户身份 |
|---|---|---|
| `DEMO_USER_ID` | V0.2 服务端固定的订单演示身份 | 否 |
| `thread_id` | V0.3 标识一段 LangGraph 对话和 Checkpoint | 否 |
| JWT `sub` / user claims | V0.4 起的当前用户及资源归属 | 验签后是 |

V0.4 已在 Router、订单 Tool Calling 和 SSE 之前完成可信身份接入：

- 前端取得并携带 JWT；Agent Core 验证签名、有效期和必要 claims。
- `get_current_user` dependency 从可信 claims 生成当前用户身份，替换 `DEMO_USER_ID`。
- Checkpoint 与对话查询同时按 `user_id + thread_id` 归属，不能仅凭 thread ID 读取会话。
- 订单工具的 `user_id` 只能来自认证上下文，不能由模型参数或调用方直接指定。
- 未认证请求返回 `401`；已认证但资源不属于当前用户时保持不可枚举的资源边界。

当前 BFF 使用服务端配置的 demo 用户签发短期 JWT，这足以验证资源归属，但不等同于生产登录。
正式登录、token issuer、刷新令牌和 RBAC 仍需在产品化阶段补齐。

## 8. 每版验收清单

每个版本结束前必须满足：

- 本版约定的业务闭环可以演示。
- 自动化测试不调用真实付费 API。
- 相关测试、Lint 和变更范围类型检查通过。
- 前后端接口契约一致。
- 服务重启、失败路径或权限边界按本版风险完成验证。
- 学习文档记录本版 Python 和 AI 知识点。
- 明确记录未覆盖场景和下一版本边界。

## 9. 计划更新规则

- 每完成一个版本，更新当前状态、实际工时和偏差原因。
- 如果实际工时超出上限 30%，先判断是学习深挖、需求扩张还是技术阻塞，不直接压缩测试时间。
- 新功能只能进入当前版本明确范围或后续版本待办，不应临时插入正在学习的后端步骤。
- 前端提前完成不会自动提高版本完成度，必须等待后端、测试、联调和复盘共同完成。
- 时间不足时优先保证当前版本闭环，企业级增强留到 V0.7，不跨版本提前铺设。
