# Ecommerce Agent System 开发与学习进度计划

> 更新日期：2026-09-19

## 1. 计划基准

本项目同时承担产品实现和 Python 学习两个目标，开发方式分为：

- 前端：由 Codex 对话直接实现，用户主要负责需求确认、视觉检查和前后端联调验收。
- 后端：采用教学模式。用户亲自编写生产业务代码，Codex 负责讲解、审查、自动化测试、Mock、验证和学习文档。编码按小概念推进，验证在一个边界清晰的功能切片完成后集中进行。
- 单次学习时间：固定按 3 小时统计和安排。
- 推荐频率：每周 6 次，保留一天用于休息、复盘或处理计划外问题。

由于后端采用教学模式，整体速度会比直接代写慢约 30%～50%，但这部分时间计入 Python、FastAPI、数据库和 Agent 工程的有效学习时间。

V1.0 原教学计划估算为 **24～36 个有效小时**，保留为计划基准；2026-09-19 用户授权 Codex 完成后端剩余工作，当前后端自动验证已完成，手动联调待验收：

- 固定 3 小时/次：约 8～12 次学习班。
- 每周 6 次时，理论投入约为 18 小时；加入教学、复盘、返工和计划外问题缓冲后，第一阶段预计约 3～5 周。
- 当前没有连续记录每次学习班的实际用时，因此剩余工时按各版本范围估算，不用未经记录的时间制造精确进度。

## 3. 用户、会话与认证现状

项目已建立服务端 JWT 认证边界，并在 V0.8 增加了本地测试账号登录流程。正式生产身份提供商、多租户和后台用户管理仍属于后续范围。三个标识不能混为一谈：

| 标识 | 当前/计划用途 | 是否是可信用户身份 |
|---|---|---|
| `DEMO_USER_ID` | V0.2 服务端固定的订单演示身份 | 否 |
| `thread_id` | V0.3 标识一段 LangGraph 对话和 Checkpoint | 否 |
| JWT `sub` / user claims | V0.4 起的当前用户及资源归属 | 验签后是 |

V0.4 已在 Router、订单 Tool Calling 和 SSE 之前完成可信身份接入：

- 前端取得并携带 JWT；Agent Core 验证签名、有效期和必要 claims。
- `get_current_user` dependency 从可信 claims 生成当前用户身份，替换 `DEMO_USER_ID`。
- Checkpoint 与对话查询同时按 `user_id + thread_id` 归属，不能仅凭 thread ID 读取会话。
- 订单工具的 `user_id` 只能来自认证上下文，不能由模型参数或调用方直接指定。
- 未认证请求返回 `401`；已认证但资源不属于当前用户时保持不可枚举的资源边界。

当前本地验收使用三个 seed 测试账号，BFF 通过 HttpOnly Cookie 管理 Access/Refresh Token；这足以验证角色和资源归属，但不等同于生产身份系统。正式身份提供商、多租户组织和后台用户管理仍需在产品化阶段补齐。

## 8. 后续阶段目标

### V1.0：支付沙箱与可审计副作用

审批通过的退款进入本地 HTTP 沙箱，后端请求幂等、签名 webhook、对账、审计和失败补偿已实现。自动补偿只补查原键；补查耗尽后需管理员处置，原键重投必须明确授权并留痕。前端处理中/成功/失败/未知结果/人工介入展示与 ADMIN 操作已接入，实际 HTTP 联调待人工验收。真实支付渠道尚未选择或接入，不能将本地沙箱通过视作真实资金验证。

### V1.1：质量与运营

建立 RAG 评估集和线上指标，关注引用准确率、拒答率、工具成功率、响应延迟、模型成本和限流命中；增加脱敏 tracing、管理员审计查询和故障告警。

### V1.2：生产化平台能力

补齐正式身份提供商、多租户组织、细粒度文档权限、配置中心、密钥轮换、备份恢复和发布回滚。此阶段关注运维和安全边界，不新增大量客服业务动作。

### V1.x：真正的 Multi-Agent 演进

只有当订单、退款、知识和人工协作在提示词、工具、权限、重试或部署节奏上产生明显分叉时，才拆成独立 Agent；拆分必须由已观察到的维护或扩展痛点驱动。

## 9. 每版验收清单

每个版本结束前必须满足：

- 本版约定的业务闭环可以演示。
- 自动化测试不调用真实付费 API。
- 相关测试、Lint 和变更范围类型检查通过。
- 前后端接口契约一致。
- 服务重启、失败路径或权限边界按本版风险完成验证。
- 学习文档记录本版 Python 和 AI 知识点。
- 明确记录未覆盖场景和下一版本边界。

## 10. 计划更新规则

- 每完成一个版本，更新当前状态、实际工时和偏差原因。
- 如果实际工时超出上限 30%，先判断是学习深挖、需求扩张还是技术阻塞，不直接压缩测试时间。
- 新功能只能进入当前版本明确范围或后续版本待办，不应临时插入正在学习的后端步骤。
- 前端提前完成不会自动提高版本完成度，必须等待后端、测试、联调和复盘共同完成。
- 时间不足时优先保证当前版本闭环，企业级增强留到 V0.7，不跨版本提前铺设。

### 教学模式下的编码与验证节奏

- 编码仍然按一个小概念、一个小步骤推进；用户完成步骤后可以继续下一个步骤，不要求每一步都立即运行完整测试。
- 测试以一个可观察的功能闭环为单位执行。例如登录、Refresh Token 轮换和退出可以连续完成，三者组成认证功能后再统一运行相关 Pytest、Ruff 和变更文件 Mypy。
- Codex 仍负责维护测试、Fake/Mock 和验证工具；只是把执行时机从“每个编码步骤之后”调整为“每个功能完成之后”，以减少上下文切换。
- 新增安全、并发、事务、幂等或数据迁移边界时，如果不先验证就可能掩盖数据破坏或越权风险，仍应在该边界完成后立即增加并运行针对性测试。
- 功能闭环完成后，先运行最小相关测试，再在版本阶段验收时运行跨功能回归；不启动 FastAPI、Docker、Worker 或其他长期服务。
