# Ecommerce Agent System 开发与学习进度计划

> 更新日期：2026-08-04

## 1. 计划基准

本项目同时承担产品实现和 Python 学习两个目标，开发方式分为：

- 前端：由 Codex 对话直接实现，用户主要负责需求确认、视觉检查和前后端联调验收。
- 后端：采用教学模式。用户亲自编写生产业务代码，Codex 每次提供一个小步骤，并负责讲解、审查、自动化测试、Mock、验证和学习文档。
- 单次学习时间：固定按 3 小时统计和安排。
- 推荐频率：每周 6 次，保留一天用于休息、复盘或处理计划外问题。

由于后端采用教学模式，整体速度会比直接代写慢约 30%～50%，但这部分时间计入 Python、FastAPI、数据库和 Agent 工程的有效学习时间。

整个项目预计还需要 **138～198 个有效小时**：

- 固定 3 小时/次：约 48～68 次学习班。
- 每周 6 次时，理论投入约为 18 小时；加入复盘、返工和计划外问题缓冲后，正常目标为 10～14 周，安全目标为 16 周。

## 2. 当前状态

V0.1 已完成：

- Turborepo、Next.js 和 FastAPI 基础目录。
- 前端工作区 Shell、共享 UI 与基础 Motion 动效。
- FastAPI 应用工厂、配置、数据库连接骨架和健康检查。
- Vitest、Testing Library、Pytest、Ruff、Mypy 和根级 Turbo 测试入口。

V0.1 尚未完成：

- 真实 OpenAI 客服接口。
- 可交互的聊天界面。
- 前后端聊天接口联调和手动验收。

当前 V0.1 约完成 **35%～40%**。下表中的 V0.1 工时为剩余工时。

## 4. 推荐周计划

以下计划按照每周 6 次、每次固定 3 小时估算，并包含学习复盘和返工缓冲：

| 周期 | 目标 | 阶段成果 |
|---|---|---|
| 第 1 周 | 完成 V0.1 | 跑通真实 AI 客服聊天 |
| 第 2 周 | 完成 V0.2 | 理解数据库和订单查询 |
| 第 3～4 周 | 完成 V0.3 | 掌握 LangGraph 状态与恢复 |
| 第 5～6 周 | 完成 V0.4 | 形成可展示的 Multi-Agent Demo |
| 第 7～8 周 | 完成 V0.5 | 跑通退款和人工审批闭环 |
| 第 9～11 周 | 完成 V0.6 | 完成企业知识库 RAG |
| 第 12～14 周 | 完成 V0.7 | 完成企业级可靠性加固 |

关键里程碑：

- 第 1 周：最小 AI 客服可用。
- 第 4 周：状态持久化完成，具备项目核心技术含量。
- 第 6 周：多 Agent + Generative UI，可作为阶段性作品展示。
- 第 8 周：退款审批闭环完成，达到业务 MVP。
- 第 11 周：RAG 完成，覆盖主要业务目标。
- 第 14 周：可靠性加固完成，形成完整项目。

## 5. 单次学习班安排

### 3 小时固定学习班

| 环节 | 时间 | 内容 |
|---|---:|---|
| 回顾 | 15 分钟 | 确认当前状态和本次验收目标 |
| 概念 | 35 分钟 | 讲解请求链、Python 概念和设计原因 |
| 编码 | 90 分钟 | 用户完成后端业务代码 |
| 验证 | 30 分钟 | 自动化测试、类型检查和调试 |
| 复盘 | 10 分钟 | 总结知识点并更新学习文档 |

前端任务可以在后端学习过程中异步推进，但每个版本仍应预留约 15%～20% 的时间用于接口契约确认、页面检查和联调验收。

## 6. 版本完成度计算

每个版本按以下权重统计：

| 项目 | 权重 | 完成标准 |
|---|---:|---|
| 后端知识点理解 | 10% | 能描述主要请求链和关键设计原因 |
| 后端业务代码 | 35% | 用户完成本版本生产业务代码 |
| 自动化测试与错误处理 | 20% | 正常、错误和关键边界测试通过 |
| 前端实现与联调 | 20% | 页面能够消费真实接口并正确展示状态 |
| 手动验收与学习复盘 | 15% | 完成验收场景和版本学习记录 |

只有五部分全部完成，版本才标记为 100%。不以“文件已经创建”或“接口可以返回一次结果”作为版本完成标准。

## 7. 每版验收清单

每个版本结束前必须满足：

- 本版约定的业务闭环可以演示。
- 自动化测试不调用真实付费 API。
- 相关测试、Lint 和变更范围类型检查通过。
- 前后端接口契约一致。
- 服务重启、失败路径或权限边界按本版风险完成验证。
- 学习文档记录本版 Python 和 AI 知识点。
- 明确记录未覆盖场景和下一版本边界。

## 8. 计划更新规则

- 每完成一个版本，更新当前状态、实际工时和偏差原因。
- 如果实际工时超出上限 30%，先判断是学习深挖、需求扩张还是技术阻塞，不直接压缩测试时间。
- 新功能只能进入当前版本明确范围或后续版本待办，不应临时插入正在学习的后端步骤。
- 前端提前完成不会自动提高版本完成度，必须等待后端、测试、联调和复盘共同完成。
- 时间不足时优先保证当前版本闭环，企业级增强留到 V0.7，不跨版本提前铺设。
